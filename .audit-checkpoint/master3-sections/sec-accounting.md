## 2. Accounting and privacy mathematics

Eighteen findings (from nineteen verified reports, after one merge). Two are high and ε-affecting —
a sensitivity/accountant mismatch in the adaptive-clipping quantile release, and the loss of the
Poisson independence hypothesis on DDP resume — and both are led here. The rest cover the new
generic Poisson PLD amplification work (#850), the calibration and budget plumbing added by the
second-audit remediations, and the coherence of the horizon-accounting, loss-scaler and
bounded-Gaussian removals.

### 2.1 Sensitivity, sampling and amplification invariants

**OPQ-400 — Adaptive clipping releases a {0,1} clipped-count query while AdaClip accounting prices it at the {−1/2,+1/2} sensitivity, under-charging the quantile stream 2× in µ.** `packages/opaque-dpsgd/src/opaque/api/dpsgd/clipping/_adaptive.py:99-122`, `packages/opaque-engine/src/opaque/api/engine/clipping/_clipped_fun.py:362-366`, `packages/opaque-accounting/src/transformations/adaclip.rs:30-34`, `packages/opaque-dpsgd/src/opaque/api/accounting/dpsgd/mechanisms/_adaclip.py:78-80,123-126` · sensitivity-accounting-mismatch · **high** · ε:yes · **CONFIRMED**.
- **Claim:** the runtime quantile release is built from a plain 0/1 clipping indicator. `_clipped_fun.py:362` computes `num_clipped = float((norms > effective_cn).sum().item())` and `:365` divides it by the realized batch size to get `clipping_rate`; `_adaptive.py:99-108` recomputes the same count and `:111-122` returns `clipping_rate + randn() * fraction_noise_std`. Under Opaque's documented add-or-remove adjacency an indicator sum moves by up to 1 when a record is added, so the released rate has per-record sensitivity ≈ 1/|B| and µ_b = 1/σ_b. The accountant charges half that: `adaclip.rs:33` returns `(1.0/(z*z) + k/(4.0*sigma_b*sigma_b)).sqrt()` with `sigma_b = expected_batch_size * fraction_noise_std` (`_adaclip.py:78-80`), i.e. µ_b = √k/(2·σ_b), and the non-Gaussian branch composes `_native.gaussian_pld(2.0 * sigma_b, ...)` `num_groups` times (`_adaclip.py:123-126`) on the same assumption. That factor of 4 is Andrew et al.'s `z = (z_Δ^-2 + (2 z_b)^-2)^-1/2`, which is only valid with the ±1/2 shift TF Privacy applies in `quantile_estimator_query.py` (`below = cast(record <= estimate) - 0.5`, with the comment that this makes the count query's sensitivity 0.5 instead of 1.0). Nothing anywhere in Opaque subtracts 0.5 from the indicator, on the single-group path (`_adaptive.py:111-122`), the per-group loops (`:546-575`, `:580-607`) or the distributed path (`_distributed.py:83-92`, which divides the global count by the realized global batch and adds the same noise). A second, smaller error compounds it: the runtime divides by the *realized* batch size while the accountant divides by the constant `expected_batch_size`, so a below-average Poisson draw raises the true sensitivity further.
- **Failure scenario:** any run that pairs `adaptive_clipped_grad` with `dpsgd_acc.adaclip(...)` — including `DPTrainer(clipping_mode="adaptive")`, which wires that pairing itself at `_dp_trainer.py:4471-4480` with the shared default `fraction_noise_std=0.05`, since `_CLIPPING_KWARGS["adaptive"]` exposes only `target_quantile` and `clipping_norm_max` (`_training_arguments.py:213-217`). The quantile term's µ is understated by exactly 2× (4× in variance) and the reported ε is not an upper bound. Measured with the repo's own accountant and prebuilt Rust extension at δ=1e-5, plain-Poisson DP-SGD: the single-group default (nm=1.1, W=256, N=50 000, T=1000) reports 0.7316 against a correctly-priced 0.7354 (0.5 % low), but per-group configurations — documented and supported at `docs/user-guide/clipping.md:481-495` — are far worse because `num_groups` multiplies the mispriced term: K=8 at W=32, nm=0.8, T=1000 reports 1.3536 against 5.3562 (3.96×), and K=16 at nm=0.6 reports 4.6988 against 16.1743 (3.44×).
- **Evidence:** `_clipped_fun.py:362-366` and `:383-393` (0/1 indicator, realized-batch denominator); `_adaptive.py:99-108`, `:111-122`, `:546-575`, `:580-607`; `_distributed.py:83-92`; `adaclip.rs:30-34`; `_adaclip.py:78-80` and `:123-126`; `_dp_trainer.py:4471-4480` and `_training_arguments.py:213-217` (trainer wiring at the shared default); `docs/user-guide/clipping.md:230-249,481-495` (the same pairing taught as a recipe, with no mention of any 1/2 shift); TF Privacy's `quantile_estimator_query.py` as the primary source for the convention the formula assumes; `test_adaptive.py:349-356` checks only the clipped-fraction convention, never the sensitivity.
- **Fix:** preferably shift the released statistic to match the analysis — release `(Σ_i (b_i − 0.5)) / expected_batch_size + N(0, fraction_noise_std²)` and add 0.5 back after noising, using the *public* `expected_batch_size` as the divisor, which fixes both halves at once (this is what TF Privacy does). The alternative is to keep the 0/1 indicator and correct the accountant to `sqrt(1/z² + k/σ_b²)`, dropping the `/4`, and to charge the realized-batch worst case. Either way, add a regression test that pins `AdaClip.effective_noise_multiplier` against the sensitivity the runtime actually realizes, plus a cross-validation test against dp_accounting's adaptive-clipping composition.
- **Notes:** high rather than critical because `clipping_mode` defaults to `"fixed"` (`_training_arguments.py:560`), so adaptive clipping is opt-in, and the single-group error is only ~0.5 %; the 3–4× cases need many per-group quantile releases at small batches. Issue #345 ("Bind AdaClip released statistic to the parameters the accountant charges") appears in the 2026-08-27 open snapshot but not in either 2026-09-13 list and was recorded closed as not-planned, so this is not currently tracked.

**OPQ-401 — DDP resume restores rank 0's sampler key on every rank, collapsing the per-shard streams and destroying the independent-inclusion hypothesis Poisson amplification rests on.** `packages/opaque-transformers/src/opaque/api/transformers/trainer/_dp_trainer.py:3944-3949, 5151, 5196, 1862-1877`, `packages/opaque-dpsgd/src/opaque/api/dpsgd/sampling/_poisson.py:210-222, 255-265` · sampling-amplification-mismatch · **high** · ε:yes · **CONFIRMED**. *(merges three independently reported instances: "DDP resume collapses every rank's Poisson sampler stream to rank 0's", "Resuming a DDP run restores rank 0's sampler key on every rank", "DDP resume installs rank 0's sampler snapshot on every rank".)*
- **Claim:** on a fresh start the trainer folds the rank into the sampler key (`_dp_trainer.py:3944-3949`), which is what makes each shard's Bernoulli(q) mask independent — but that branch is reached only when `ctx.current_sampler is None` (`:3938`). The sampler snapshot instead carries an *absolute* stream key (`_state_dict_poisson` stores `key_seed`/`key_impl`, `_poisson.py:210-222`) and is written by the saving rank only: `self._save_dp_runtime(staging_dir, ctx)` at `:5196` sits inside `if _distributed.should_save(a, self._ddp):` (`:5151`), and `should_save` returns `ddp.is_world_zero` by default (`_distributed.py:211-222`) — unlike the per-rank RNG snapshot at `:5205-5210`, which every rank deliberately writes. Restore then runs unconditionally on every rank (`:1862-1877`) and `_from_state_dict_poisson` rebuilds from the snapshot's seed with no rank re-fold (`_poisson.py:255-265`). All five sampler serializers do the same (`_poisson.py:261`, `_k_out_of_t.py:218`, dpftrl `_poisson.py:304`, `_b_min_sep.py:259`, `_balls_in_bins.py:260`). Because the dataset is trimmed to a multiple of `world_size` (`:3886-3908`), every shard has the same length, so from the resume point all ranks select *identical local index sets*: the global batch becomes the union of the W co-indexed records at each sampled local position. Marginals are still q, but each record's inclusion indicator is now perfectly correlated with its W−1 shard-mates, and that independence is exactly what lets the Poisson mixture decompose as (1−q)P + qQ against the same P. The in-code comment at `_dp_trainer.py:3874-3886` acknowledges the correlation and then asserts that "the per-record marginal stays Bernoulli(q) either way, so the privacy accounting is unaffected" — which is the wrong conclusion, and actively misinforms the reader.
- **Failure scenario:** a multi-GPU DP-SGD or DP-FTRL run that is checkpointed and resumed. Reproduced: two rank-folded `PoissonSampler(range(1000), 0.05, key=fold_in(key(7), r))` diverge on a fresh start (first batches `[19,29,42,…]` vs `[39,55,60,…]`), but after `from_state_dict(template_r, state_dict(rank0_sampler))` both hold `RngKey(seed=12201757873983228112, impl="opaque_threefry_like")` and emit the byte-identical batch `[20,43,76,86,160,197,215,224]`. The accounted bound is then violated: for the achievable neighbouring pair (all records zero except the target's W−1 co-indexed shard-mates at +C), the single-step hockey-stick at nm=1.1, q=0.01, W=8 is δ(ε=1.0) = 9.6e-4 by quadrature against the repo accountant's 1.3e-10 for the same step (2.0e-3 vs 2.7e-8 at ε=0.5) — a rigorous seven-order-of-magnitude violation. Over T=1000 steps the reported ε is 1.5154 while the idealized indicator-revealed mechanism needs 20.43 at δ=1e-5.
- **Evidence:** `_dp_trainer.py:3938,3944-3949` (rank fold-in only on a fresh build); `:5151,5196` with `_distributed.py:211-222` (rank-0-only DP runtime bundle) against `:5205-5210` (per-rank RNG bundle); `:1862-1877` (unconditional restore on every rank); `_poisson.py:210-222,255-265` and the four sibling serializers; the two-sampler `from_state_dict` reproduction; the quadrature evaluation of the co-indexed neighbouring pair against the accountant's own single-step δ; `_dp_trainer.py:3874-3886` (the comment asserting the accounting is unaffected); the July audit's clean-areas note certified this path for the fresh-start case only, so the resume path had never been checked.
- **Fix:** make the sampler stream key rank-derived at *restore* time rather than stored as an absolute — either persist only the rank-independent base key plus the cursor and re-apply `fold_in(base, rank)` in `from_state_dict`, or write a per-rank sampler snapshot (`dp_state.rank{r}.pt`) alongside the per-rank RNG snapshot and have each rank restore its own. Until one of those lands, fail closed: refuse to restore a sampler snapshot when `world_size > 1` unless the snapshot records the rank it was written for and that rank matches. Correct the comment at `_dp_trainer.py:3874-3886`. Lock it in with a 2-rank gloo test that saves, resumes, and asserts the ranks' post-resume index sets are disjoint in distribution (differing stream keys).
- **Notes:** the horizon figure (13.5×) is an idealization that assumes error-free per-step indicator decoding — at W=8 the separation is 6.4σ, so decoding error is ~7e-4; the single-step violation is exact. For cyclic-Poisson and balls-in-bins the shared key also fixes a common partition or bin assignment, so the co-participation structure becomes permanent rather than per-step.

**OPQ-402 — `paired_noise_stddevs` documents a second-moment sensitivity of `first * first`, which is `normalize_by` times too small for the averaged release the library produces.** `packages/opaque-engine/src/opaque/api/engine/noise_allocation.py:205-211` · docs-safety · **low** · ε:no · **CONFIRMED**.
- **Claim:** the `second` parameter doc says the second-stream per-record sensitivity Δ² is "typically obtained as ``first * first`` element-wise", and the `first` doc says that for DP-SGD averaged clipping `first = C / n`. That recipe yields C²/n². The quantity actually released on the second stream is `(Σ_i g_i ⊗ g_i) / normalize_by`, whose per-record L2 bound is `‖g ⊗ g‖₂ / n ≤ ‖g‖² / n = C² / n` — a factor of `normalize_by` larger. Every shipped path uses the correct convention: `_clipped_fun.py:386-394` sets `squared_bound = (current * current) / normalize_by`, `_adaptive.py:396-397` does the same, and `resolve_paired_clipped` (`noise_allocation.py:255-281`) and `dpftrl/noise/_second_moment.py:146-150` both read the bound off `ClippedPytree.max_norm`. `_clipped_fun.py:466-473` even states the rule correctly for its own `second_moment` parameter. So nothing in the library follows its own docstring.
- **Failure scenario:** a monorepo contributor wiring a new paired first/second-moment mechanism follows the documented recipe with averaged clipping and passes C²/normalize_by² where the release has sensitivity C²/normalize_by, under-noising the second stream by a factor of `normalize_by` while the accountant still reports `gaussian(nm)`. No shipped call site does this, and with the default `normalize_by = 1.0` the recipe is not even wrong — `first * first = C²`.
- **Evidence:** `noise_allocation.py:205-211` (the two parameter docs, verbatim); `_clipped_fun.py:386-394` and `_adaptive.py:396-397` (the correct convention); `_clipped_fun.py:466-473` (the correct wording, in the same package); `noise_allocation.py:255-281` and `dpftrl/noise/_second_moment.py:146-150` (both consumers read the bound rather than recomputing it).
- **Fix:** change the `second` parameter doc to "the per-record squared bound divided by the same `normalize_by` as the first stream — `C**2 / normalize_by`, not `first * first`", mirroring the wording already used for `clipped_fun`'s `second_moment`. Add a unit test asserting that `resolve_paired_clipped` on a `second_moment=True` clipping output satisfies `second == first * normalize_by * first`, so the relation stays pinned.
- **Notes:** the module header states that `noise_allocation` is **not** a supported public API and it is imported only from `opaque.api.*` internals, so the reduced claim is documentation-only: there is no current miscalibration anywhere in the shipped tree. The original report was filed as ε-affecting; the verifier established that no shipped path follows the recipe, so it does not move any reported ε today.

### 2.2 Poisson PLD amplification (#850)

**OPQ-403 — `dpsgd_acc.poisson()` now accepts any `DpProcess` as its base, so a whole-horizon or already-amplified process is silently re-subsampled and priced as a mechanism no Opaque sampler realizes.** `packages/opaque-dpsgd/src/opaque/api/accounting/dpsgd/amplification/_poisson.py:22, 40-47, 161-172, 185-186` · amplification-semantics / accounting-fail-open · **medium** · ε:yes · **CONFIRMED**. *(merges two reports: "poisson() now accepts whole-horizon and composed processes as its base, silently accounting a mechanism no Opaque sampler realizes", "Generalizing `dpsgd_acc.poisson()` to any DpProcess removed the inner-type guard, so an already-amplified whole-horizon process is silently re-subsampled and reports a smaller epsilon".)*
- **Claim:** 3b22a6af ("feat(accounting): generalize Poisson PLD amplification (#850)") replaced `_Inner = Gaussian | AdaClip | NonPrivate` with `_Inner = DpProcess` (`_poisson.py:22`) and replaced the factory's `match` on the inner type with `if not isinstance(self.inner, DpProcess)` (`:40-47`) — the only inner-type check left on the plain path. The plain branch then calls `_native.poisson_pld(self.inner.pld(...), self.sample_rate)` for every inner type (`:161-172`). Nothing at construction or PLD time distinguishes a per-step base from a `DpHorizonProcess` subclass (`KOutOfT`, `CyclicPoisson`, `BallsInBins`, `BMinSep`) or from a `Repeated`/`Composed` spine, even though the library owns exactly that marker — `core/_horizon.py` documents `DpHorizonProcess` as "a complete fixed-horizon process that cannot be accounted by prefixes" and `docs/reference/accounting.md:283` types `k_out_of_t` as returning one. `Poisson.__post_init__` simply never consults it. The truncated path still enforces `Gaussian | AdaClip | NonPrivate` (`:91-99`), so the two branches now disagree about what a valid base is, and the factory docstring still reads "Returns a single-step process — compose externally with ``* num_steps`` for full-training privacy" (`:185-186`) while `docs/reference/accounting.md:232` and `docs/user-guide/accounting.md:114` advertise "any Opaque `DpProcess`" with no caveat. The resulting number is a valid bound only for "draw one dataset-level Bernoulli(q) coin per record, then run the entire horizon on the survivors" — a mechanism no shipped Opaque sampler implements, since `PoissonSampler` redraws every step and `KOutOfTSampler` has no dataset-level coin.
- **Failure scenario:** a user writes `dpsgd_acc.poisson(dpsgd_acc.k_out_of_t(dpsgd_acc.gaussian(1.0), k=2, t=100, allocation="block"), 0.01)`. It is accepted at HEAD and reports `epsilon_at(1e-5) = 0.0097389` for the whole 100-step run, against 1.2339386 for the same horizon accounted correctly (`k_out_of_t` alone, which is what `KOutOfTSampler` realizes) — 127× higher — and 0.7180658 for the closest realizable per-step reading `poisson(gaussian(1.0),0.01)*100`. Before #850 the same call raised `TypeError`. The double-amplification variant is equally silent: `ftrl_acc.poisson(mf_gaussian(1.0, band_mf_strategy(bands=8)), sample_rate=0.08, n_steps=1000)` reports 6.2286, and wrapping that process again in the DP-SGD factory reports 2.6974 (2.3× smaller) with no error or warning; `da.poisson(da.poisson(gaussian(1.1),0.01),0.01)*1000` gives 0.0098 instead of 1.5154. Neither side of the step/horizon boundary is guarded — `dpsgd_acc.k_out_of_t(...) * 2` also succeeds, returning 1.6398.
- **Evidence:** `_poisson.py:22` (`_Inner = DpProcess`), `:40-47` (the sole check), `:161-172` (unconditional native call), `:185-186` (the unchanged per-step docstring), `:91-99` (the surviving guard on the truncated branch); `git show 3b22a6af^:…/_poisson.py` ends with `case Gaussian() | AdaClip() | NonPrivate(): pass; case _: raise TypeError(...)`, and 3b22a6af replaced it while adding tests that exercise only a generic *per-step* base (`test_amplification.py:163-167`, `test_accepts_generic_dp_process`); `core/_horizon.py:12-18` (the unconsulted marker); `docs/reference/accounting.md:232` and `docs/user-guide/accounting.md:114` (the uncaveated widening); all epsilon figures reproduced with the checked-in extension.
- **Fix:** keep the generalization but gate it in `Poisson.__post_init__` (so direct construction and deserialization are covered, not just the factory): reject `DpHorizonProcess` inners outright — they already describe a complete amplified run — and reject inners that already contain an amplification node (`Poisson`, `ParallelPoisson`, `KOutOfT`, `CyclicPoisson`, `BMinSep`, `BallsInBins`) unless the caller opts in with a flag that names the one-dataset-level-coin model. Apply the same guard to `ParallelPoisson` and to `dpftrl_acc.poisson`. Document that model separately from the DP-SGD per-step reading, say which sampler realizes it (none today), and cover it with a test asserting `dpsgd_acc.poisson(ftrl_acc.poisson(...), q)` raises.
- **Notes:** reachable only by a user writing the nested composition — no Opaque factory, trainer path, calibration helper or documented example does so, and DP-FTRL runs go through `opaque.dpftrl.accounting.poisson`, whose `_Inner` is still `MfGaussian`. The returned numbers are the mathematically correct accounting for the expression the caller wrote, so the loss is intent-checking rather than unsound arithmetic; the acceptance is now test-pinned and documented, which is why the second report's severity was cut to low. What remains real in both is the fail-open direction: an expression that used to raise now silently returns a smaller ε. Not independently verified: what mechanism, if any, the returned bound is correct for beyond the single dataset-level-coin reading — that was reasoned about but not proved against the Feldman–Shenfeld subsampling theorem cited in `poisson.rs:17-20`.
