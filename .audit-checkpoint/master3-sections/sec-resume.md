## 4. Checkpoint, resume and distributed state

Ten findings from the state-compatibility sweep and the trainer fix-verification pass. The first
group covers what survives a `resume_from_checkpoint` — model weights, sampler cursors, noise
streams, optimizer state and their cross-checks; the second covers two trainer regressions in the
`torch_compile` path and one in the custom-loss path that the same fix-verification pass turned up.

### 4.1 Checkpoint and resume state

**OPQ-445 — PEFT/LoRA resume silently restores no adapter weights: the model continues from fresh random init while the accountant, noise counter, sampler cursor and optimizer state are all restored faithfully.** `packages/opaque-transformers/src/opaque/api/transformers/trainer/_dp_trainer.py:5479-5481` (resume), `:4910-4912` (`load_best_model_at_end`), `:4974-4976` (adapter file discovery) · silent-state-loss · **critical** · ε:no · **CONFIRMED**.
- **Claim:** `_load_model_weights` ends with `if not mutated: strict = not self._is_peft; self._model.load_state_dict(new_state, strict=strict)` (`:5479-5481`), and `_load_best_model` repeats those same three lines verbatim (`:4910-4912`). For a PEFT-wrapped model `self._is_peft` is `True` (set at `:467` from an `isinstance(PeftModel | PeftMixedModel)` test), so the load runs with `strict=False`. That is fatal here, because the two key spaces do not overlap at all: `_save_model_artifacts` (`:5244-5247`) checkpoints through `self._model.save_pretrained(...)`, and PEFT's `save_pretrained` strips the adapter name from every key (`base_model.model...lora_A.weight`), while the live module's `state_dict()` keys carry it (`base_model.model...lora_A.default.weight`). Every saved key is therefore "unexpected" and every model key "missing"; the returned `_IncompatibleKeys` is discarded and nothing is logged. The resumed run continues with the *freshly initialised* adapter while `dp_state.pt` (clip/noise/sampler state), `dp_optimizer.pt`, `accountant.json` and `rng_state.pth` are all restored correctly, so every signal a user would look at says the resume worked. There is no second restore path: `_apply_runtime_state` (`:5548-5573`) rewrites `ctx.trainable_params` only for `ScheduleFreeState`, so the trainable parameters come from the unmutated module. Hugging Face's own `Trainer` — whose behaviour DPTrainer claims parity with — uses `model.load_adapter(resume_from_checkpoint, active_adapter, is_trainable=True)` for exactly this case (`transformers/trainer.py:3440` on resume, `:3502` for best-model load); `grep` for `set_peft_model_state_dict`, `get_peft_model_state_dict` or `load_adapter` across `packages/` (including `opaque-alignment`) returns nothing.
- **Failure scenario:** any PEFT/LoRA run — the documented DPTrainer fine-tuning shape — resumed with `trainer.train(resume_from_checkpoint='.../checkpoint-N')`. Reproduced end to end on the real trainer in the repo venv (peft 0.20.0, transformers 5.15.1; tiny GPT-2 + LoRA r=4 on `c_attn`, 4 steps, `save_steps=2`, `clipping_norm=1.0`, `noise_multiplier=1.0`, `use_cpu`): instrumenting `_load_model_weights` during the resume prints `_is_peft: True`, `weights changed by load?: False`, `post-load == checkpoint?: False`, `post-load == fresh-init?: True`, and the run then completes to `global_step=4` reporting `privacy_epsilon=0.8132` with no warning. With dropout disabled so the trajectory is otherwise deterministic, the continuous run logs `grad_norm` 0.836132824 and 0.929508567 at steps 3 and 4 while the resumed run logs 1.277820706 and 1.491086841 on the same batches and the same reported epsilon; the final `|Δw|` over the LoRA tensors is 0.1716. The user gets a plausible-looking completed DP run whose model has thrown away all prior learning — and in a DP setting the loss is not recoverable by re-running, because the dataset's privacy budget for those steps has already been spent. The identical three lines at `:4910-4912` make `load_best_model_at_end=True` a no-op for PEFT as well: reproduced with `eval_steps=2`/`save_steps=2` and the best checkpoint recorded as checkpoint-2, the final in-memory adapter equals checkpoint-4 (the last checkpoint), not the best — exactly the outcome the flag's own docstring at `:4877-4880` says it exists to prevent. Non-PEFT full-model checkpoints take the `strict=True` branch and are unaffected by *this* defect (see OPQ-448 for what happens to them instead).
- **Evidence:** `_dp_trainer.py:5479-5481` (`strict = not self._is_peft`, return value discarded); `:4910-4912` (same code in `_load_best_model`); `:467` (`_is_peft`); `:5244-5247` (`save_pretrained`); `:4974-4976` (`adapter_model.safetensors` probed by `_read_weights_file`); `:5548-5573` (`_apply_runtime_state` does not re-point trainable params); measured key sets — disk `base_model.model.transformer.h.0.attn.c_attn.lora_A.weight` vs module `...lora_A.default.weight`; the isolated check that the literal call at `:5481` returns 4 unexpected / 33 missing keys and restores nothing without raising; the empty `grep` for the PEFT state-dict helpers; `transformers/trainer.py:3440, :3502` for the upstream idiom; `packages/opaque-transformers/tests/validation/test_dp_guarantees.py:347-349, :567-572` (every existing resume test asserts only `global_step` and `privacy_epsilon`, never restored weights); `docs/user-guide/huggingface/dptrainer.md:79-88` documents resume with no caveat.
- **Fix:** branch on `self._is_peft` in both `_load_model_weights` and `_load_best_model` and call `peft.set_peft_model_state_dict(self._model, new_state, adapter_name=self._model.active_adapter)` — or `self._model.load_adapter(ckpt_dir, active_adapter, is_trainable=True)`, matching upstream. Independently of the PEFT branch, capture the `_IncompatibleKeys` result at both sites and raise when *no* key matched: that single assertion converts this class of failure from silent to loud for any future key-space skew. Lock it in with a regression test that checkpoints a LoRA run, resumes in a fresh process, and asserts the live adapter tensors equal the checkpoint's (not the fresh init), plus a `load_best_model_at_end=True` variant asserting the final adapter equals the *best* checkpoint rather than the last. The existing resume tests should gain a weight assertion so that "resume works" can no longer mean only "the step counter advanced".
- **Notes:** `affects_epsilon` is false — the reported epsilon correctly prices the mechanism that actually executed. What is destroyed is the *product* of that spend. Reaching it needs two explicit opt-ins (a PEFT-wrapped model plus `resume_from_checkpoint` or `load_best_model_at_end`), which is the only argument for high rather than critical; the verifier kept critical because the failure is silent and total at the library's primary documented fine-tuning shape and the wasted budget is unrecoverable.

**OPQ-446 — DP-SGD resume keeps the checkpoint's Poisson `sample_rate` in the sampler but rebuilds the accountant from the new arguments, so a batch-size change across a resume under-reports epsilon behind a `log.warning`.** `packages/opaque-dpsgd/src/opaque/api/dpsgd/sampling/_poisson.py:229-266` (esp. `:256`, `:260`); `packages/opaque-transformers/src/opaque/api/transformers/trainer/_dp_trainer.py:4525-4545` (accountant built from current args), `:5679-5760` (warn-only drift branch) · sampler-accounting-desync · **high** · ε:yes · **CONFIRMED**.
- **Claim:** `_from_state_dict_poisson` rebuilds the sampler with `sample_rate=float(sd["sample_rate"])` and `truncated_batch_size=sd.get("truncated_batch_size")` taken from the *snapshot*, using the template only for `n_steps` and the data source; its one equality guard is on `num_samples`. Meanwhile `_build_mechanism` closes the accountant's `dpsgd_acc.poisson(gaussian(nm), sample_rate=...)` over the *current* `ctx.sample_rate = train_batch_size / effective_dataset_size`. `RuntimeCheckpoint.sample_rate` is tagged `drift="dp_relevant"` (`_checkpoint.py:232-234`), but `_warn_on_arg_drift` raises only when the saved mechanism is not `"gaussian"` or the resume is a horizon resume — so for plain Poisson DP-SGD it emits a `log.warning` and continues. The sampler then draws at the saved q while the accountant charges the new q. This is the same defect class as the `RandomAllocationSampler.num_bins` desync (closed #792), and the fix for it (#1019, `fix(dpsgd)!: reject allocation-law drift on sampler restore`) added a `k`/`t`/`allocation` equality guard to `KOutOfTSampler` **only** (`_k_out_of_t.py:204-212`). Every sibling codec still resolves the same class of amplification parameter in favour of the snapshot: `PoissonSampler` (`sample_rate`, `truncated_batch_size`), `CyclicPoissonSampler` (`sample_rate`, `bands`, `partition_type`), `BMinSepSampler` (`bands`, `sampling_prob`), `BallsInBinsSampler` (`num_bins`), `SequentialBatchSampler` (`batch_size`). `truncated_batch_size` is not a `RuntimeCheckpoint` field at all, so drifting it produces no diagnostic whatsoever.
- **Failure scenario:** reproduced verbatim on HEAD (GPT-2 + LoRA, N=64, `privacy_noise_multiplier=1.0`, default Poisson sampling, δ=1e-5, `save_steps=4`, `use_cpu`). Phase 1 at `per_device_train_batch_size=32` (q=0.5) realises batch sizes `[32,25,29,31,36,26,41,36]` and reports `privacy_epsilon=4.75151`. Resuming checkpoint-4 with `per_device_train_batch_size=8` (q=0.125) realises `[36,26,41,36]` for steps 5-8 — bit-identical to the continuous q=0.5 run, which proves the restored sampler is still drawing Bernoulli(0.5) — yet reports `privacy_epsilon=3.25344`, i.e. 31.5 % below the epsilon of the mechanism that actually ran (the post-resume steps add ≈0.025 each instead of ≈0.40). The resumed `accountant.json` carries four `"sample_rate": 0.125` Poisson nodes for the post-resume steps while the same checkpoint's `dp_state.pt` records `sampler_state.sample_rate: 0.5`. The only diagnostics are three `log.warning` lines (`Resume arg drift on sample_rate (dp_relevant, DP-SGD): saved=0.5, current=0.125`, plus `expected_steps_per_epoch` and `expected_batch_size`); none of them states which value won, or that the reported epsilon no longer bounds what ran. Reaching it requires changing `per_device_train_batch_size` (or the dataset-size denominator) on resume of an all-defaults Poisson DP-SGD run — an ordinary operational action.
- **Evidence:** `_poisson.py:256` and `:260` (snapshot wins for `sample_rate` / `truncated_batch_size`; only `num_samples` guarded); `_dp_trainer.py:4525-4545` (accountant over `ctx.sample_rate`); `_checkpoint.py:232-234` (`drift="dp_relevant"`) and `_dp_trainer.py:5679-5760` (raise only for non-gaussian or horizon resume); `_checkpoint.py:229-247` (`truncated_batch_size` absent from the compared fields); `_k_out_of_t.py:204-212` (the #1019 guard that was not replicated); the same snapshot-wins pattern in `packages/opaque-dpftrl/src/opaque/api/dpftrl/sampling/_poisson.py`, `_b_min_sep.py`, `_balls_in_bins.py`, `_sequential.py`; the reproduced epsilon pair and the two contradicting artifacts in the same checkpoint directory.
- **Fix:** mirror the #1019 guard in every remaining sampler codec — compare the snapshot's amplification-law parameters (`sample_rate`, `truncated_batch_size`, `bands`, `sampling_prob`, `num_bins`, `partition_type`, `batch_size`) against the template and raise `ConfigurationError` on any difference, exactly as the existing `num_samples` check does — and make `sample_rate`/`expected_batch_size` drift fatal rather than warn-only whenever a cursor-carrying sampler was restored. Add `truncated_batch_size` to `RuntimeCheckpoint`'s compared fields. The regression test is a two-phase trainer resume that changes `per_device_train_batch_size` and asserts a raise; note that the sampler-side behaviour is currently *pinned* by `packages/opaque-dpsgd/tests/sampling/test_poisson_state_dict.py:88-106` (it asserts `restored.sample_rate == 0.2` against a template built at 0.5), so that test has to be updated as part of the fix.
- **Notes:** the codec's snapshot-wins choice and the accountant's current-args choice are each individually intentional; the defect is the trainer-level desync between them. Kept at high rather than critical because a diagnostic *is* printed and the direction is fail-open only when the resume batch size is *smaller* — a larger resume batch over-charges epsilon and is conservative. #792 and #1019 are both closed and neither covers this pairing.

**OPQ-447 — DDP resume installs rank 0's sampler snapshot on every rank, collapsing the per-rank Poisson streams the rank fold exists to keep independent while the accountant keeps pricing i.i.d. Poisson amplification.** `packages/opaque-transformers/src/opaque/api/transformers/trainer/_dp_trainer.py:3944-3949` (per-rank fold, fresh builds only), `:5151` + `:5197` (rank-0-only `_save_dp_runtime`), `:1861-1877` (unconditional restore on every rank), `:3872-3885` (the acknowledging-but-wrong comment); `packages/opaque-dpsgd/src/opaque/api/dpsgd/sampling/_poisson.py:255-265` · distributed-resume-desync / amplification-hypothesis-violation · **high** · ε:yes · **CONFIRMED**. *(merges three independent reports: the engine-distributed fix-verification pass, the privacy-invariants sweep and the state-compatibility sweep.)*
- **Claim:** on a fresh start the trainer folds the rank into the sampler key — `if self._ddp.world_size > 1: sampler_key = fold_in(sampler_key, self._ddp.rank)` (`:3944-3949`), reached only in the `ctx.current_sampler is None` branch at `:3938` — which is what makes each shard's Bernoulli(q) mask independent and therefore makes the union of the shard draws an exact Poisson sample of the whole population, the hypothesis `acc.poisson` prices at the global rate (`:1494`). But the sampler snapshot stores an *absolute* stream key (`_state_dict_poisson` writes `key_seed`/`key_impl`) and is written only by the saving rank: `_save_dp_runtime(staging_dir, ctx)` at `:5197` sits inside `if _distributed.should_save(a, self._ddp):` (`:5151`), and `should_save` returns `ddp.is_world_zero` by default (`_distributed.py:211-222`). The restore, `ctx.current_sampler = from_state_dict(ctx.current_sampler, saved_sampler_state)` (`:1874-1876`), is guarded only by `resume_path is not None and saved_sampler_state is not None and not a.ignore_data_skip` — no rank branch — and `_from_state_dict_poisson` rebuilds `RngKey(seed=int(sd["key_seed"]), impl=str(sd["key_impl"]))` with no re-fold. Every sampler family does the same (`_k_out_of_t.py:218`, `dpftrl/_poisson.py:304`, `_b_min_sep.py:259`, `_balls_in_bins.py:260`). Since `local_shard` hands out contiguous disjoint shards of equal length (`_shard.py:20-35`, dataset trimmed to a multiple of world size), every rank then selects the *same local offsets* in its own shard, so the `world_size` records sharing a local index are included or excluded together with probability 1 for the rest of training. The in-source comment at `:3872-3874` justifies deferring this with "the per-record marginal stays Bernoulli(q) either way, so the privacy accounting is unaffected" — which is false: amplification needs the target record's inclusion indicator to be *independent* of the rest of the sample, not merely Bernoulli(q) marginally.
- **Failure scenario:** any DPTrainer DDP run with `world_size > 1`, default `save_on_each_node=False` and default `ignore_data_skip=False`, using per-record Bernoulli sampling (`poisson` or `cyclic_poisson`), that is resumed from a checkpoint — the ordinary preempt-and-restart path. Verified on a real 2-rank Gloo run (the `packages/opaque-transformers/tests/distributed/_ddp_runner.py` fixtures, `save_steps=2`, resume from checkpoint-2, `use_cpu`): the fresh phase gives each rank a distinct stream key (rank 0 seed 1950457451192556855, rank 1 seed 16528425509808239245), and after `resume_from_checkpoint` **both** ranks report 1950457451192556855. Isolated at the sampler level too: `PoissonSampler(range(1000), 0.05, key=fold_in(key(7), r))` yields different first batches for r=0/1, and after both templates are passed through `from_state_dict` with rank 0's snapshot both hold `RngKey(seed=12201757873983228112)` and emit the byte-identical batch `[20,43,76,86,160,197,215,224]`. The accounting consequence was then quantified by numerically integrating the hockey-stick divergence of the executed group-sampled mechanism against the amplified one the accountant charges, with worst-case aligned co-indexed gradients: at `noise_multiplier=1.0`, q=0.01, world_size=4 the real per-step δ at ε=1 is 1.26e-3 versus the charged 2.73e-9 (ratio 4.6e5); at q=0.1, W=4 it is 1.27e-2 versus 2.07e-4; at nm=2.0, q=0.1, W=8 it is 6.8e-4 versus 1.1e-10. In the well-separated regime the executed δ converges to exactly `q · δ_Gaussian(unamplified)` — subsampling buys only the factor q, not the subsampled-Gaussian bound. A single-step reference at σ=1, q=0.01, δ=1e-5 gives ε=0.199 for the intended independent Poisson versus 2.399 for the W=2 correlated pair (3.139 at W=4). No warning is emitted at resume, and the `distributed` marker lane has no sampler-snapshot case.
- **Evidence:** `_dp_trainer.py:3944-3949` (the fold, fresh builds only, `:3938`); `:5151` + `:5197` with `_distributed.py:211-222` (`should_save` → `is_world_zero`); `:1874-1876` (restore, no rank branch) versus `:5205-5210`, where `_save_rng_state` already writes one file per rank — the per-rank-artifact pattern exists and was simply not applied to the sampler; `_checkpoint.py:69-75` (`rng_state_path` is per rank); `_poisson.py:255-265` and the four sibling codecs (absolute key restored verbatim); `_shard.py:20-35` (contiguous equal shards); the 2-rank Gloo key collapse; the sampler-level identical-batch reproduction; the hockey-stick integrations above; `_dp_trainer.py:3872-3885` for the incorrect justification and the acknowledged caveat.
- **Fix:** write the sampler snapshot per rank, unconditionally of `should_save`, next to the per-rank RNG snapshot (`sampler_state_{rank}.pt`, or move `sampler_state` out of the rank-0 bundle) and restore this rank's own file; alternatively persist only the rank-independent root key plus the cursor and re-apply `fold_in(base, rank)` inside `from_state_dict`. Until one of those lands, fail closed: refuse to restore a sampler snapshot when `world_size > 1` unless the snapshot records the rank it was written for and that rank matches, rather than proceeding silently. Correct the comment at `:3872-3874` — independence, not the marginal, is what the amplification theorem needs. The regression test belongs in the `distributed` lane: run two Gloo ranks, checkpoint, resume, and assert the ranks' sampler stream keys are still distinct and their emitted index sets differ.
- **Notes:** the worst-case magnitude needs an adversarial dataset with aligned co-indexed gradients; the qualitative loss of amplification is unconditional and applies to every sampling mode, since all five codecs restore a saved absolute key (for cyclic-Poisson and balls-in-bins the shared key also fixes a common partition/bin assignment). The original state-compat report rated this medium and reasoned the magnitude rather than measuring it; verification ran the 2-rank reproduction and the divergence integrals and raised it to high, on the grounds that it is reachable at stock settings with no warning and fails open. The in-code note that this is "tracked for the multi-GPU work" is not backed by any open issue found in the milestone/issue exports (the FSDP2 issues #55-58 are a different subject).

**OPQ-448 — full-finetune resume and `load_best_model_at_end` crash for every tied-embedding model, because the checkpoint omits `lm_head.weight` but the loader is strict.** `packages/opaque-transformers/src/opaque/api/transformers/trainer/_dp_trainer.py:5242-5247` (save via `save_pretrained`), `:5469-5481` (`strict = not self._is_peft`), `:4892-4912` (same in `_load_best_model`) · resume-break · **high** · ε:no · **CONFIRMED**.
- **Claim:** `_save_model_artifacts` writes checkpoint weights with `self._model.save_pretrained(output_dir, safe_serialization=self.args.save_safetensors)`, and `save_pretrained` drops tied parameters (those in `_tied_weights_keys`) from the file. `_load_model_weights` then reads that file and calls `load_state_dict(new_state, strict=True)` for every non-PEFT model, so the absent `lm_head.weight` is a hard error; neither loader calls `tie_weights()` afterwards nor filters `_tied_weights_keys`. On transformers 5.15.1 a tied Llama reports `_tied_weights_keys == {'lm_head.weight': 'model.embed_tokens.weight'}`, `save_pretrained` writes 11 tensors with `lm_head.weight` absent while `model.state_dict()` contains it, and the strict load raises. Only the single-file path is affected — the sharded branch of `_read_weights_file` already loads with `strict=False`.
- **Failure scenario:** any non-PEFT (full-finetune) DPTrainer run whose model ties input and output embeddings. Reproduced at the trainer level twice: (a) tiny GPT-2, 4 steps, `save_steps=2`, `trainer.train(resume_from_checkpoint=.../checkpoint-2)` raises `RuntimeError: Error(s) in loading state_dict for GPT2LMHeadModel: Missing key(s) in state_dict: "lm_head.weight".` from `_dp_trainer.py:5481`, before the first post-resume step; (b) a `LlamaConfig(tie_word_embeddings=True)` full finetune, whose checkpoint-2 contains `accountant.json`, `config.json`, `dp_optimizer.pt`, `dp_state.pt` and `model.safetensors`, fails identically for `LlamaForCausalLM`. The saved `model.safetensors` for the GPT-2 case holds 28 tensors including `transformer.wte.weight` and no `lm_head.weight`. Because `_load_best_model` shares the code, a completed full-finetune run with `load_best_model_at_end=True` crashes at the *end* of training — after the privacy budget has been spent — leaving the run's result unrecoverable through the trainer.
- **Evidence:** `_dp_trainer.py:5242-5247` (`save_pretrained`); `:5469-5481` and `:4892-4912` (`strict = not self._is_peft`, no `tie_weights()`, no tied-key filtering); the transformers-5.15.1 isolation showing `lm_head.weight` present in `state_dict()` and absent from the written file; the two trainer-level tracebacks; the checkpoint tensor inventory; the sharded branch's `strict=False` contrast; every resume test in `packages/opaque-transformers/tests/validation/test_dp_trainer.py` uses the `gpt2_with_lora` fixture, i.e. PEFT and therefore `strict=False`, which is why nothing catches it.
- **Fix:** load with `strict=False` and then verify coverage explicitly — compute `missing = set(model.state_dict()) - set(new_state)`, subtract `getattr(model, "_tied_weights_keys", [])` (or its mapping keys), raise if anything remains, and call `model.tie_weights()` after loading. Doing the explicit-coverage check is what keeps this from degrading into OPQ-445's silent no-op. Pin it with a resume test over a `tie_word_embeddings=True` config (a 2-layer `LlamaConfig` is enough) plus a `load_best_model_at_end=True` variant, so at least one resume test exercises the non-PEFT branch.
- **Notes:** one correction to the original report: `tie_word_embeddings` is *not* the class default for `LlamaConfig`/`Qwen2Config`/`Qwen3Config` on transformers 5.15.1 (all `False`); it is the default for `GPT2Config` and `Gemma2Config`, and it is set `True` in the published `config.json` of many real Hub checkpoints (Llama-3.2, Qwen3, SmolLM, and every Gemma/Gemma2/Gemma3). The failure is loud and not epsilon-affecting, but it breaks a documented core workflow, and in the `load_best_model_at_end` variant it breaks it only after the budget is gone.

**OPQ-449 — MF noise state carries no derivation-version or execution-identity tag except for BISR, so the #1018 λ-CGD stream change and any strategy-hyperparameter drift restore silently onto a different mechanism on the direct-library path.** `packages/opaque-dpftrl/src/opaque/api/dpftrl/noise/_state_codec.py:26` (`_LAYOUT_VERSION = 1`), `:369-446` (`_load`); `packages/opaque-dpftrl/src/opaque/api/dpftrl/noise/_lambda_cgd.py:281, 293`; `packages/opaque-dpftrl/src/opaque/api/dpftrl/noise/_bisr.py:43-51, 96-119` · missing-version-guard · **low** · ε:yes · **CONFIRMED**.
- **Claim:** `MFNoiseState`'s wire format records only `layout_version`, `_step_counter`, `_rng_key`, the max-norm latch and the inner-state field *names*. It records neither the strategy hyperparameters (bands, `max_buffers`, momentum, alpha/beta, `lambda_`, `normalized`), nor the horizon (`n_steps`, `min_sep`, `max_participations`), nor the compute dtype, nor a version of the noise-derivation law. BISR alone got an execution identity from `d09d7b9a fix(dpftrl): bound BISR noise state by bandwidth (#886)` — `_BisrExecutionIdentity(version, inverse_coefficients, normalized, n_steps, compute_dtype)`, validated in `_validate_saved_execution_identity` — and BISR consequently fails closed on all of these; no sibling strategy got one. Separately, `f2d90d61 fix(random)!: namespace lambda-CGD noise stream (#1018)` changed λ-CGD's per-step key derivation from `rng_fold_in(st._rng_key, step)` to `_mf_gaussian_column_key(st._rng_key, step)` without bumping `_LAYOUT_VERSION` (still 1); `git log -S"_LAYOUT_VERSION" -- _state_codec.py` returns only 1794504b (#901). The repo's designated versioning seam, `packages/opaque-base/src/opaque/api/base/serialization/_compat.py`, is still an empty placeholder.
- **Failure scenario:** reachable only through direct library use of `opaque.dpftrl.noise` + `opaque.serialization`, not through DPTrainer. Re-ran the accept/reject matrix on HEAD: an `MFNoiseState` saved mid-stream and restored into a template built with a different `n_steps` (band_mf 8→16) is **accepted** and emits different noise (−0.76381 → −0.70943); `momentum` 1.0→0.5 accepted (−0.76381 → −1.01377); bsr `alpha` 0.9→0.7 accepted (−1.10275 → −1.03146); `lambda_cgd` `lambda_` 0.5→0.9 accepted (−1.27672 → −1.77366).
