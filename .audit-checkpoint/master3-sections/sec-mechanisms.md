## 3. DP-SGD, DP-FTRL, engine and optimizers

Twenty findings, IDs **OPQ-420 … OPQ-439**, grouped by subsystem and severity-ordered within each
group. Two are high (both in `opaque-optimizers`), one is high in the distributed resume path, five
are medium, and the remainder are low. Three are ε-affecting.

### 3.1 DP-SGD (`opaque-dpsgd`)

**OPQ-420 — `dpsgd_acc.poisson()` lost its inner-mechanism guard and now silently amplifies processes that are already amplified or already whole-horizon.** `packages/opaque-dpsgd/src/opaque/api/accounting/dpsgd/amplification/_poisson.py:21, 39-46, 91-98, 162-173` · fail-open-validation · **medium** · ε:yes · **CONFIRMED**.
- **Claim:** commit 3b22a6af (`feat(accounting): generalize Poisson PLD amplification`, #850) widened `_Inner` from `Gaussian | AdaClip | NonPrivate` to `DpProcess` (`:21`) and deleted the factory's `match inner: … case _: raise TypeError("poisson() requires a Gaussian, AdaClip, or NonPrivate inner mechanism, …")`. `Poisson.__post_init__` now checks only `isinstance(self.inner, DpProcess)` (`:39-46`), the surviving type guard lives inside the truncated branch alone (`:91-98`), and the non-truncated path falls straight through to `_native.poisson_pld(self.inner.pld(...), self.sample_rate)` (`:162-173`). The generic PLD-subsampling transform is sound for the model it implements — subsample the dataset once, then run the inner mechanism — but that is not what any Opaque runtime does, and nothing signals that the composed expression has left the DP-SGD model. The DP-FTRL sibling still refuses: `packages/opaque-dpftrl/src/opaque/api/accounting/dpftrl/amplification/_poisson.py:279-288` raises unless the inner is an `MfGaussian` with a BandMf/Identity strategy, so the two stacks now disagree on strictness.
- **Failure scenario:** the guard removal was deliberate and documented (3b22a6af also updated `docs/reference/accounting.md` and `docs/user-guide/accounting.md` to say plain Poisson accepts any `DpProcess`, and replaced `test_rejects_non_gaussian` with `test_rejects_non_process`), but nothing replaced it for inners that are themselves participation models or compositions. Reproduced on the current tree: `dpsgd_acc.poisson(dpsgd_acc.poisson(dpsgd_acc.gaussian(1.1), 0.01), 0.01) * 1000` reports `epsilon_at(1e-5) = 0.009837` where the correct single-amplification DP-SGD figure is `1.515442` — a 154× understatement with no error and no warning, where the pre-3b22a6af tree raised `TypeError`. Likewise `dpsgd_acc.poisson(dpsgd_acc.k_out_of_t(dpsgd_acc.gaussian(1.1), k=2, t=100, allocation="block"), 0.1)` reports `0.108651` against the `0.970344` the horizon process reports on its own, for a mechanism ("Poisson-subsample the dataset, then run k-out-of-t on the subsample") that no Opaque sampler implements. A user who reaches either expression through a helper or config path and calibrates noise against it deploys at far less noise than the claimed epsilon requires.
- **Evidence:** `_poisson.py:21` (`_Inner = DpProcess`), `:39-46` (the only remaining check), `:91-98` (guard surviving in the truncated branch only), `:162-173` (fall-through to the native transform); `git show 3b22a6af -- …/dpsgd/amplification/_poisson.py` shows the `-_Inner = Gaussian | AdaClip | NonPrivate` / `+_Inner = DpProcess` swap and the factory-guard deletion; `git show 4b13d82:…/_poisson.py:170-175` holds the removed `TypeError`; executed numbers 1.5154423566628403 / 0.009836885508304796 and 0.970343695110472 / 0.10865088995647369; `packages/opaque-dpftrl/src/opaque/api/accounting/dpftrl/amplification/_poisson.py:279-288` for the asymmetry.
- **Fix:** restore a guard in `Poisson.__post_init__` that rejects inners which are themselves participation models or compositions — `DpHorizonProcess` (`KOutOfT`, `BMinSep`, `BallsInBins`, `CyclicPoisson`), `Poisson` / `ParallelPoisson`, and the `Composed` / `Repeated` wrappers — while keeping the generalisation for genuine single-release mechanisms, and name the construction the user probably meant (`poisson(gaussian(nm), q) * n_steps`) in the message. Lock it in with a test that asserts each rejected inner class raises, alongside the existing `test_rejects_non_process`.
- **Notes:** the documented single-amplification path (`poisson(gaussian(nm), q) * T`) is unchanged and correct, and the Gaussian path was cross-validated against `dp_accounting` at four `(nm, q, T)` points (Opaque conservative by 7e-5 to 6.7e-4). Triggering this needs a user-constructed expression, and the composition layer is permissive elsewhere too — `k_out_of_t(...) * 10` is likewise accepted with no guard, returning 3.096846 — which is why the verifier held this at medium rather than raising it.

**OPQ-421 — `adaclip` is priced with `train_batch_size` under `sampling_mode="k_out_of_t"`, whose expected batch size is `dataset_size * k / n_steps`.** `packages/opaque-transformers/src/opaque/api/transformers/trainer/_dp_trainer.py:1472, 4470-4479, 4495` · runtime-accounting-mismatch · **medium** · ε:yes · **CONFIRMED**.
- **Claim:** `_build_mechanism` wraps the base Gaussian in `dpsgd_acc.adaclip(..., expected_batch_size=expected_batch_size, num_groups=num_groups)` (`:4470-4479`) *before* it branches on `a.sampling_mode` (`:4495`), and `expected_batch_size = a.train_batch_size` (`:1472`). That is the right expectation only for Poisson sampling, where `sample_rate = train_batch_size / dataset_size`. The k-out-of-t sampler's own expectation is `num_samples * k / t` (`packages/opaque-dpsgd/src/opaque/api/dpsgd/sampling/_k_out_of_t.py:110-116`) with `t = n_steps` from `_steps_breakdown` (`_dp_trainer.py:4740-4767`), so the two agree only when the user happens to set `k == num_train_epochs`, and never reliably when `max_steps` is set. Nothing derives, constrains or warns about `k`: `_training_arguments.py:1311-1345` checks only that `k` and `allocation` are present and that `allocation` is `"block"` or `"total"`, and `:1281-1292` resolves adaptive to fixed only for DP-FTRL mechanisms. The coupling used to be structural — at the audit baseline the equivalent parameter was `num_bins = expected_steps_per_epoch`, computed from `train_batch_size` (`git show 4b13d82:…/_dp_trainer.py:4264-4277`) — and fc44ec8d (#761) replaced the derived `num_bins` with a free user-supplied `k` without re-establishing the link.
- **Failure scenario:** `dataset_size=10000`, `per_device_train_batch_size=32`, `num_train_epochs=3` (so `steps_per_epoch=313`, `n_steps=939`), `clipping_mode="adaptive"`, `sampling_mode="k_out_of_t"`, `sampling_kwargs={"k": 1, "allocation": "block"}`. `TrainingArguments` accepts this with no warning (verified by execution, `clipping_mode` still `"adaptive"`). The sampler draws batches averaging `10000 * 1 / 939 = 10.65` examples and `_adaptive.py:580-600` noises the realised rate `num_clipped / batch_size`, i.e. an absolute count noise of `realised_batch * 0.05`; the accountant is handed `expected_batch_size = 32`, i.e. `sigma_b = 32 * 0.05`. Reproduced with the real factories: `k_out_of_t(adaclip(gaussian(1.0), expected_batch_size=32), k=1, t=939, allocation="block").epsilon_at(1e-5) = 0.16464` (effective noise multiplier 0.954480), against `0.49026` (0.728991) when the process is built with the sampler's true expectation of 10.65 — a 3.0× understatement in the unsafe direction. The mismatch is unbounded when `max_steps` is set, because `_steps_breakdown` then uses `t = max_steps` with no link to `train_batch_size` at all. The direction reverses and becomes conservative when `k > num_train_epochs`.
- **Evidence:** `_dp_trainer.py:1472` (`expected_batch_size = a.train_batch_size`), `:4478` (passed into the adaclip wrapper), `:4495` (the sampler branch that comes after); `_k_out_of_t.py:110-116` (`num_samples * k / t`); `_dp_trainer.py:4740-4767` (`n_steps` derivation); `_training_arguments.py:1281-1292, 1311-1345` (no `k` constraint, adaptive not resolved away for Gaussian); `_adaptive.py:106-121, 580-600` (the runtime noise scale); the executed epsilon pair 0.16464 / 0.49026; `git show 4b13d82:…/_dp_trainer.py:4264-4277` for the removed structural coupling; `packages/opaque-transformers/tests/validation/test_dp_guarantees.py:237-259` is the only trainer k-out-of-t guarantee test and it uses the default `clipping_mode="fixed"`.
- **Fix:** compute the accounting expected batch size from the sampling model rather than from `train_batch_size` — for `sampling_mode="k_out_of_t"` pass `dataset_size * k / n_steps` into `dpsgd_acc.adaclip`, and use the same value for `normalize_by` so the gradient scale matches the batches actually drawn. Alternatively derive `k` from `num_train_epochs` and reject an explicit contradicting `k`, restoring the pre-#761 coupling. Either way add a `TrainingArguments` check (or a loud warning naming both values) that `dataset_size * k / n_steps` is within tolerance of `train_batch_size`, and a guarantee test that runs the adaptive + k-out-of-t combination.
- **Notes:** held at medium because `clipping_mode` defaults to `"fixed"` and `sampling_mode` to Poisson, so it takes two explicit opt-ins plus a `k` that disagrees with the horizon; within that configuration the understatement is silent and ~3×.

**OPQ-422 — `AdaClip.__post_init__` guards only the non-positive half of its range, so `expected_batch_size=inf` still prices the quantile release as free.** `packages/opaque-dpsgd/src/opaque/api/accounting/dpsgd/mechanisms/_adaclip.py:40-62, 74-80, 164-173` · accounting-validation / fail-open · **low** · ε:no · **CONFIRMED**.
- **Claim:** the #859 validation added to close OPQ-310 checks `fraction_noise_std <= 0`, `expected_batch_size <= 0` and `num_groups < 1 or != int(...)`. None of those comparisons is true for `+inf`, so an `AdaClip` deserialized with `expected_batch_size=inf` or `fraction_noise_std=inf` is accepted, `sigma_b` becomes infinite, the `K / (4 * sigma_b^2)` term in `adaclip_sensitivity` vanishes, and `effective_noise_multiplier` collapses to the bare inner multiplier. That is the same "prices adaptive clipping as free" outcome, in the same threat model, that the comment at `:40-44` says the validation exists to prevent. Separately, `inner` is validated by the `adaclip()` factory (`:164-173`) but not by `__post_init__`, so a foreign inner makes the `match` in `effective_noise_multiplier` (`:74-80`) fall through and return `None` from a `-> float` property.
- **Failure scenario:** a hand-edited or corrupted accountant checkpoint whose `AdaClip` JSON carries `Infinity` for `expected_batch_size` (or `fraction_noise_std`) is rebuilt by `from_state_dict` without error, and the run's adaptive-clipping quantile releases are then unaccounted. Verified through the real codec (`state_dict(adaclip(gaussian(1.1), expected_batch_size=250.0, num_groups=4))`, field replaced, `from_state_dict`): `effective_noise_multiplier` collapses from 1.0957654 to 1.1 and `poisson(..., 0.01).epsilon_at(1e-5)` drops from 0.14418328 to 0.14229776 — bit-identical to the unamplified-quantile `poisson(gaussian(1.1), 0.01)` figure, and matching to five digits what the original OPQ-310 report measured for `num_groups=0`. `NaN` in either field is also accepted by `__post_init__` but fails closed downstream (`ValueError: Infinite epsilon bounds: [NaN, NaN]`), so `+inf` is the surviving fail-open value. Separately, `AdaClip(inner=poisson(gaussian(1.1), 0.01), ...)` constructs without error and its `effective_noise_multiplier` returns `None`; its `pld()` takes the generic `case _` branch and is conservative (6.038 vs 1.515 over 1000 steps), and no shipped path consumes the `None`.
- **Evidence:** `_adaclip.py:40-44` (the comment stating the validation exists so deserialization "cannot produce an instance that prices the quantile release as free"), `:45-56` (the only bounds are `<= 0` comparisons), `:74-80` (the un-guarded `match`), `:164-173` (factory-only `inner` validation); the codec run producing 1.1 / 0.1422977567766371 against the untampered 1.0957654 / 0.14418327866598055; the `NaN` path failing closed in the native PLD.
- **Fix:** require finiteness — `if not math.isfinite(self.fraction_noise_std) or self.fraction_noise_std <= 0`, and the same for `expected_batch_size`; apply the same treatment to `Gaussian.noise_multiplier` in `mechanisms/_gaussian.py:28`. Add an `isinstance(self.inner, (Gaussian, NonPrivate))` check to `AdaClip.__post_init__` so the dataclass and the factory agree, and give `effective_noise_multiplier` an explicit `case _: raise` instead of an implicit `None`. Lock it in with a round-trip test that tampers each numeric field with `inf`, `-inf` and `NaN` and asserts `from_state_dict` raises.
- **Notes:** ε marked **no** despite the mispricing being real, because the verifier characterised this as a fail-open hardening gap rather than a live epsilon defect: neither `inf` value is reachable through the `adaclip()` factory or an untampered serialization round-trip, so it needs a corrupted or hand-edited checkpoint. It is exactly the threat model the code comment claims to cover.

**OPQ-423 — the #881 random-allocation memoisation is dead along its most valuable dimension, because `epsilon_at` folds a Monte-Carlo-only field into the cache key.** `packages/opaque-accounting/src/opaque/api/accounting/core/_random_allocation_cache.py:29-46` · efficiency · **low** · ε:no · **CONFIRMED**.
- **Claim:** `epoch_pld` is an `lru_cache` keyed on `(noise_multiplier, t, k, config)` where `config` is the whole frozen `DiscretizationConfig` — `mc_resolution` and `mc_failure_probability` included, and the dataclass is frozen so both participate in `__eq__`/`__hash__` (`discretization.py:17-40`). `DpProcess.epsilon_at` overwrites `mc_resolution` with `min(configured, delta / 2.0)` before calling `pld()` (`core/_base.py:212-227`) while `delta_at` does not, so every distinct delta and every switch between the two entry points produces a distinct key. The underlying transform is delta- and Monte-Carlo-independent: `packages/opaque-accounting/src/amplification/random_allocation.rs:164-227` plus `Accuracy::derive` / `alloc_remove` / `alloc_add` read only `discretization`, `log_mass_truncation_bound`, `max_conv_grid`, `max_grid_size` and `tail_mass_truncation`. The per-process `pld_cache` keys on the same config object, so it misses in lockstep.
- **Failure scenario:** any epsilon-vs-delta sweep, or simply `epsilon_at(1e-5)` followed by `epsilon_at(1e-6)` or `delta_at(eps)`, on a k-out-of-t or balls-in-bins/identity process recomputes the delta-independent O(G²) geometric-grid transform from scratch. Measured at `k=8, t=512` with default discretization: 16.5 s for `eps(1e-5)`, 0.01 s for the identical repeat, then 16.6 s for `eps(1e-6)` and 16.5 s for `delta_at(3.0)`, with `epoch_pld.cache_info()` reporting `hits=0, misses=3`. Efficiency only — the returned epsilon values are correct.
- **Evidence:** `_random_allocation_cache.py:29-35` (`@functools.lru_cache(maxsize=8) def epoch_pld(noise_multiplier, t, k, config)`); `core/_base.py:212-227` (`effective_resolution = min(configured_resolution, delta / 2.0)` passed down as `mc_resolution`); `random_allocation.rs:164-227` (no `mc_*` field reaches the transform); the timing/cache-info run above; `packages/opaque-dpsgd/tests/accounting/test_k_out_of_t_cache.py:35-39` asserts `misses == 1` across two direct `process.pld(**_CFG)` calls, which the per-process `pld_cache` satisfies on its own, so the test cannot observe this.
- **Fix:** key `epoch_pld` on only the fields the transform reads — `(noise_multiplier, t, k, config.discretization, config.log_x_mass_truncation_bound, config.max_grid_size, config.max_conv_grid)` — or give `DiscretizationConfig` a `deterministic_key()` projection that drops `mc_resolution` / `mc_failure_probability` and hash that. Then retarget the regression test at `epsilon_at` with two different deltas and assert `epoch_pld.cache_info().hits >= 1`.
- **Notes:** the original title's "never serves a hit" is too strong and has been narrowed: the verifier observed `hits=1` when a structurally different process (`allocation="total"` at the same `nm`/`k`/`t`) queried the same delta, so `epoch_pld` does deduplicate across distinct processes at a fixed delta. Delta is its one useless dimension. The original report's `delta_at(3.0) = 6.67e-09` did not reproduce (measured 0.0), which is immaterial to the defect.

But the sampler snapshot is written **only** by the saving rank — `_save_dp_runtime` (`:5273-5310`, which serialises `ctx.current_sampler` into the single `DP_STATE_NAME` file) is called at `:5197` inside `if _distributed.should_save(a, self._ddp)`, world rank 0 by default (`trainer/_distributed.py:211-222`) — and is restored by **every** rank: the resume load at `:1175-1178` is not rank-gated and `:1871-1877` runs `ctx.current_sampler = from_state_dict(ctx.current_sampler, saved_sampler_state)` unconditionally, overwriting the rank-folded template. - **Failure scenario:** multi-rank DDP (`torchrun --nproc-per-node>=2`) with checkpointing on, the job preempted and restarted with `resume_from_checkpoint`. Each rank owns a disjoint `local_shard` (`:3909-3913`) and on a fresh run draws an independent mask; after the resume point every rank replays rank 0's stream and therefore selects the **same local offsets** in its own disjoint shard, so records sharing a local index across the W shards are included or excluded together with probability 1 for the rest of training — while the accountant keeps pricing independent Poisson. Magnitude, re-derived by numerical hockey-stick integration at σ=1, q=0.01, δ=1e-5 for a single step: the intended independent Poisson mechanism has ε = 0.199 (dominating pair `N(0)` vs `(1-q)N(0) + qN(1)`), while the neighbouring pair actually realisable with W=2 correlated records — `(1-q)N(0)+qN(1)` vs `(1-q)N(0)+qN(2)` — gives ε = 2.399, and W=4 gives 3.139. No warning, no accountant signal, and `docs/user-guide/distributed-trainer.md` has no resume section at all.
- **Evidence:** `_dp_trainer.py:3945-3950` (the fresh-run per-rank fold, in the `current_sampler is None` branch only); `:5197` + `:5273-5310` and `trainer/_distributed.py:211-222` (snapshot written under `should_save`, world rank 0 by default); `:1175-1178` and `:1871-1877` (load and `from_state_dict` on every rank, not rank-gated); `dpsgd/_poisson.py:219, 255-261` and the identical pattern at `_k_out_of_t.py:181/218`, `dpftrl/_poisson.py:259/304`, `_b_min_sep.py:219/259`, `_balls_in_bins.py:221/260` (stream key restored verbatim); `:1489-1494` (accounting is `acc.poisson` at the global rate); the sampler-level index-list reproduction above; the hockey-stick figures 0.19945 / 2.39891 / 3.13866; `:3869-3873` (the incorrect justification) and `:3878-3885` (the in-source acknowledgement that "resuming a DDP run currently restores rank 0's per-rank key on every rank, re-introducing the cross-rank correlation after the resume point"), which maps to no issue in either tracked list.

### 3.5 Optimizers (`opaque-optimizers`)

OPQ-436 and OPQ-437 are the same root cause in two optimizers — a missing negative-`v` fallback in the private second-moment branch — and **share a single fix**: the `torch.where(v > 0, v, signal²).clamp(min=floor)` guard that Adam, RMSprop and AdEMAMix already apply. They should be fixed and tested together.

**OPQ-436 — Adadelta's private second-moment branch diverges geometrically because it lacks the negative-`v` fallback every sibling optimizer applies.** `packages/opaque-optimizers/src/opaque/api/optimizers/_adadelta.py:115-117, 251-253, 267-273, 321` · numerical-correctness · **high** · ε:no · **CONFIRMED**.
- **Claim:** in the `noisy_squared_grads` (private second-moment) branch, `_scale_by_adadelta` guards a possibly-negative second moment with only `v_g_corrected = torch.clamp(v_g_corrected, min=0.0)` (`:251-253`). Adam (`_adam.py:194-197`: `torch.where(v_hat > 0, v_hat, m_hat * m_hat).clamp(min=bc_floor)`), RMSprop (`_rmsprop.py:126-128`) and AdEMAMix (`_ademamix.py:136-140`) all instead fall back to the squared signal — exactly what `_adam.py`'s own comment says the fallback is for: "Falling back to the squared first moment keeps the update magnitude ≈1 … instead of collapsing the denominator to `bc_floor` → infinity update." In Adadelta the collapse is worse than a one-off spike because it feeds back: clamping to 0 makes `rms_g = sqrt(0 + eps) = 1e-3` at the default `eps=1e-6` (`:115-117`, `:321`), so `coef = rms_dx_prev / rms_g` is inflated ~1e3×, `dx = coef * g` is inflated with it, and `v_dx_new = rho * v_dx + (1 - rho) * dx * dx` (`:273`) carries the inflation into the next step's `rms_dx_prev`. `_bias_correction.py:31-34` already states that "the separate `bc_floor` clamp seen in some optimizers belongs to the *private second-moment* branch (`noisy_squared_grads`), where v-hat … can be genuinely negative" — Adadelta has that branch and has neither the clamp nor the fallback.
- **Failure scenario:** with the opt-in paired release (`mf_gaussian_noise(..., second_moment_strategy=...)`, documented at `docs/reference/optimizers.md:110-140`) routed into `adadelta` — the LR-free optimizer the same docs recommend "when learning-rate tuning is hard" (`optimizers.md:48`) — `_chain.py:138, 169-176` auto-routes the privatised stream in because the scaler's `update()` accepts the kwarg (`_adadelta.py:158`). - **Evidence:** `_adadelta.py:251-253` (clamp only, no `where`-fallback, no positive floor), `:115-117` + `:321` (`_rms` and the default `eps=1e-6`, giving `rms_g = 1e-3` on a fully clamped `v_g`), `:267-273` (the `coef` → `dx` → `v_dx_new` feedback path), `:158` (the accepted kwarg); `_adam.py:194-197`, `_rmsprop.py:126-128`, `_ademamix.py:136-140` (the sibling guards) and `_adam.py`'s comment; `_bias_correction.py:31-34`; `_chain.py:138, 169-176` (auto-routing) and `_second_moment.py:174` plus `docs/reference/optimizers.md:110-140` (the documented producing flow); the 10-step fixture divergence and the d=100000 regime numbers; `tests/test_adadelta.py:296-307` (one-step bound) against `tests/test_adam.py:502-518` (the honest version — adamw stays at ~1.0e-3 over 8 steps).
