## 7. Public API surface and documentation

This group covers the public surface the three breaking removals and the new exception taxonomy
(#760) left behind, the façade export lists, and the published documentation — the reference pages,
the user guides, the mechanism pages and the tutorials whose stored outputs are served verbatim on
the docs site. It closes with the residue of two earlier fix verifications (alignment chat-template
and auditing dataset-guard work) and with the coverage claims that are supposed to keep this class
from recurring.

The single most serious entry here is **OPQ-517**: the flagship LLM fine-tuning tutorial publishes
ε = 1.09 for a run whose accounted cost is 8.99 because it prices an adaptively-clipped training
loop with the plain Gaussian chain. That is a wrong number on a public page, not a latent code
defect, and it is the only high-severity finding in the section.

### 7.1 Error contracts and the #760 exception taxonomy

**OPQ-505 — `calibrate()`'s runtime-unsafe fallback re-runs the whole binary search at the undivided Monte Carlo failure probability but still reports it as the overall union bound.** `packages/opaque-accounting/src/opaque/api/accounting/core/calibration.py:331-341, 353` · accounting-confidence · **medium** · ε:no · **CONFIRMED**.
- **Claim:** `calibrate()` deliberately splits its Monte Carlo failure budget across probes so that the adaptive binary search is covered by a union bound: `probe_count = max_iterations + 2` (`calibration.py:303`) and `probe_config = replace(overall_config, mc_failure_probability=overall/probe_count)` (`:304-309`). The primary path is sound because the calibrated parameter is re-evaluated exactly once, non-adaptively, under `overall_config` (`:320-330`) — that single evaluation is what licenses reporting the undivided value. The `if not runtime_safe:` fallback added by aa15e6ac (#912) instead re-runs the *entire* search via `_calibrate_impl` while still inside `with _use_discretization(overall_config)` (`:331-341`), so every probe of that second search consumes the full `mc_failure_probability`, and `achieved = result.achieved` is taken straight from an adaptively selected probe with no non-adaptive re-check. Line 353 then sets `result.mc_failure_probability = overall_config.mc_failure_probability`, contradicting the field's own docstring at `:79-81` ("Overall failure probability covering every adaptive Monte Carlo probe").
- **Failure scenario:** at the library's true defaults (`mc_resolution=1e-5`, `mc_failure_probability=1e-6`, 2 940 252 MC samples) a user calls `cal.calibrate(cal.epsilon_budget(8.0, delta=1e-5), lambda nm: balls_in_bins(mf_gaussian(nm, blt_strategy()), num_bins=5, n_steps=20), 0.5, 8.0)`. Instrumenting `_calibrate_impl` shows two invocations: the probe-config search converges, the single runtime re-evaluation lands above budget, and the fallback then performs 19 iterations / ≈21 probes each spending the undivided 1e-6 instead of 1e-6/102. `CalibrateResult.mc_failure_probability` is nevertheless reported as 1e-6 (mc_confidence 0.999999) where the honest simultaneous coverage is ≈2.1e-5 — a failure mass larger than the δ = 1e-5 the user calibrated at, i.e. the reported confidence is optimistic by roughly the probe count.
- **Evidence:** `calibration.py:303` and `:304-309` (probe split); `:320-330` (the single non-adaptive re-evaluation that protects the primary path); `:331-341` (the fallback search inside `_use_discretization(overall_config)`); `:353` (the reported value); `:79-81` (the documented contract); reproduced twice by wrapping `_calibrate_impl`, once at `mc_resolution=1e-2` and once at full defaults, both showing `invocations=2` with the second search at 1e-6 and 19 iterations; `packages/opaque-dpftrl/tests/accounting/test_b_min_sep.py:229` pins exactly the reported-equals-configured behaviour and `packages/opaque-dpsgd/tests/accounting/test_calibration.py:608` only pins that the fallback yields a safe `achieved`.
- **Fix:** either run the fallback search under `probe_config` too and take `achieved` from one non-adaptive re-evaluation at the chosen parameter, or report the honest union (`overall_config.mc_failure_probability * probes_performed`) when the fallback fires. Add a regression test that forces the fallback (monkeypatch `budget.evaluate` to return an unsafe value once) and asserts the reported `mc_failure_probability` covers every probe performed.
- **Notes:** the verifier reduced the ε dimension. Re-evaluating the same converged process at 1e-6/22, 1e-6 and 2.2e-5 gave ε = 7.98944 / 7.99999 / 8.01978 — under 0.3 % spread — and at default `mc_resolution` the value was insensitive, so the defect is a mislabelled confidence field rather than a materially understated epsilon. The fallback is reachable at default discretization and default tolerance, not only in a corner case, though it is configuration-dependent (a smaller `num_bins=2` / `n_steps=4` case did not trigger it).

**OPQ-508 — `risk_at` lets a Rust `clamp` panic escape as `pyo3_runtime.PanicException`, which `except Exception` cannot catch.** `packages/opaque-accounting/src/pld/mod.rs:420-426`; Python entry points `packages/opaque-accounting/src/opaque/api/accounting/core/_base.py:335-369` and `_accountant.py:195-205` · robustness · **low** · ε:no · **CONFIRMED**.
- **Claim:** `Pld::risk_at` computes `let max_risk = prior.min(1.0 - prior); metrics::bayes_risk(self, prior).clamp(0.0, max_risk)`. For any `prior` outside [0, 1] or NaN, `max_risk` is negative or NaN, and Rust's `f64::clamp` panics when `min > max` or either is NaN. Neither the Rust function, the PyO3 shim (`src/python/pld.rs:135-136`, `fn risk_at(&self, prior: f64) -> f64` with no `PyResult`) nor the Python wrapper (`_base.py:369` forwards `prior` untouched) guards the domain. The panic unwinds through pyo3 as `pyo3_runtime.PanicException`, whose MRO is `(PanicException, BaseException, object)` — it does *not* derive from `Exception`.
- **Failure scenario:** reproduced on `da.poisson(da.gaussian(1.0), 0.01) * 100` with the in-tree extension: `prior` 0.0 → 0.0, 0.5 → 0.4745867 and 1.0 → 0.0 return normally, while 1.5, −0.5, ±inf, NaN and 1e300 each panic in `core::num::f64` ("min > max, or either was NaN. min = 0.0, max = -0.5") and surface as `pyo3_runtime.PanicException` with a Rust backtrace on stderr. A defensive `try: log(acct.risk_at(prior)) except Exception: pass` does not absorb it (only `except BaseException` does), so a caller who passes 50 for "50 %" kills the process instead of getting a `ConfigurationError`.
- **Evidence:** `pld/mod.rs:420-426` (the variable-bound clamp); `src/python/pld.rs:135-136` (unguarded shim); `_base.py:335-369` and `_accountant.py:205` (unvalidated forwarding); the reproduced MRO and the non-firing `except Exception`; `packages/opaque-accounting/src/opaque/api/accounting/core/_budgets.py:235-236, 252` — `RiskBudget` is safe only because it validates `0 < prior < 1` at construction.
- **Fix:** guard before the clamp — return an error for a non-finite or out-of-[0,1] `prior`, or compute `max_risk = prior.min(1.0 - prior).max(0.0)` — and, better, validate in `_base.py:335` and raise `ConfigurationError('prior must be in [0, 1], got ...')` so the failure lands in the public taxonomy.
- **Notes:** severity was cut from medium: the finding's "aborts the whole training process" framing is speculative, since no trainer or accounting path calls `risk_at` during training and every in-library consumer is guarded, so the crash happens where the bad prior is supplied. The verifier did not audit the other variable-bound clamps named in the fix sketch (`pld/metrics.rs:273, 373`, `amplification/poisson.rs:301`); those clamp against `1.0 - infinity_mass`, which stays in [0, 1].
