## 6. Public-release posture, packaging and CI

The repository is public (Apache-2.0, `visibility: public` per the GitHub API) and the
documentation site at `https://jetbrains-research.github.io/opaque/` is live, so every item
below is live exposure rather than backlog. Two are immediately actionable by anyone who
reads the README today: the documented extras install commands resolve to an unrelated PyPI
project, and six of the ten published distribution names are unregistered on PyPI.

### 6.1 Packaging, distribution and the PyPI namespace

**OPQ-480 — Every documented "Extras" install command omits the registry index and therefore installs an unrelated PyPI project named `opaque`.** `docs/getting-started/installation.md:33-36`, `README.md:78-81` · packaging/supply-chain · **medium** · ε:no · **CONFIRMED**. *(merges two reports of the same defect: "Published install instructions install an unrelated PyPI project instead of Opaque", "Public install documentation's 'Extras' commands omit the registry index and resolve to an unrelated PyPI project named `opaque`".)*
- **Claim:** Opaque is published only to `https://packages.jetbrains.team/pypi/p/fed/python/simple/`, and the first install block on each page carries that index — `installation.md:19-28` and `README.md:67-73` both show `pip install opaque --index-url https://packages.jetbrains.team/pypi/p/fed/python/simple/` and the `uv --index` equivalent. The "Extras" block immediately below drops the flag entirely: four bare commands, `pip install "opaque[auditing]"`, `"opaque[dpftrl]"`, `"opaque[transformers]"` and `"opaque[all]"` (`installation.md:33-36`, `README.md:78-81`). `--index-url` does not persist across shell invocations, so pip resolves the name `opaque` from PyPI — where it belongs to a different project: `opaque` 1.0.0, summary "python libopaque wrapper", author Stefan Marsiske, home page `https://github.com/stef/libopaque`. pip only *warns* about extras a distribution does not provide, so nothing stops the install. A grep for `packages.jetbrains.team` across `README.md` and `docs/` returns only those four correct lines; two further bare commands exist outside the audited blocks, `docs/user-guide/index.md:9` ("Install with `pip install opaque` (plus `opaque[...]` extras)") and `docs/alignment/trainers.md:319` (`pip install opaque[trl]`).
- **Failure scenario:** a reader of the live installation page or the README copies any of the four Extras commands. Reproduced verbatim twice in clean virtualenvs: `pip install --dry-run --no-deps "opaque[auditing]"` prints `Using cached opaque-1.0.0.tar.gz (10 kB)` then `Would install opaque-1.0.0`; `pip install --dry-run "opaque[all]"` emits only `WARNING: opaque 1.0.0 does not provide the extra 'all'` and resolves to `opaque-1.0.0 pysodium-0.7.18`. Worse, the extras form *replaces* a working install: with a real `opaque` 0.15.0 already present in the venv, `pip install "opaque[all]"` still reported `Would install opaque-1.0.0`, whereas the bare `pip install opaque` in the same state was a no-op (`Requirement already satisfied ... 0.15.0`). The user is left with a libopaque C-binding wrapper and no Opaque sub-wheel at all, so `import opaque.dpftrl` raises `ModuleNotFoundError`; a CI image built from these docs silently ends up with the wrong `opaque` distribution. The same hazard applies to `uv add`, since the second block never re-specifies `--index`. No privacy guarantee is affected — the failure is loud at import time.
- **Evidence:** `docs/getting-started/installation.md:19-28` (correct block) vs `:33-36` (bare extras); `README.md:67-73` vs `:78-81`; `https://pypi.org/pypi/opaque/json` → name `opaque`, version 1.0.0, summary "python libopaque wrapper", author Stefan Marsiske; the JetBrains simple index serves the real `opaque-0.15.0-py3-none-any.whl` anonymously; clean-venv dry-run reproductions with pip 24.0 as quoted above; live page `https://jetbrains-research.github.io/opaque/latest/getting-started/installation/` returns 200 and renders all four commands; `docs/user-guide/index.md:9`, `docs/alignment/trainers.md:319`.
- **Fix:** carry the index into every documented command — either append `--index-url https://packages.jetbrains.team/pypi/p/fed/python/simple/` to each extras line, or restructure the section to configure the index once persistently (`pip config set global.index-url ...` / `[[tool.uv.index]]`) and say explicitly that the setting applies to the whole page. Add one sentence warning that the `opaque` name on PyPI is an unrelated project. Fix the two stray bare commands in `docs/user-guide/index.md` and `docs/alignment/trainers.md` and the same block in `packages/opaque-accounting/README.md`. Lock it in with the ARC-011 post-build scenario the contract already describes: extract each tagged install command from the documentation, run it verbatim in a clean container against the generated artifacts, and assert `import opaque.dpsgd` succeeds.
- **Notes:** the wrong package is a benign third-party wrapper today rather than attacker-controlled, which is why the verifier held this at medium; the same missing-index pattern is, however, exactly the shape a dependency-confusion upload against OPQ-481's unregistered names would exploit. ARC-011 is marked **Planned** in `.junie/architecture-contracts.md`, so no existing check covers documented install commands.

**OPQ-481 — Defensive PyPI registration covers only four of the ten published distribution names; the other six are unregistered and claimable.** `README.md:34-45`, `pyproject.toml:83-94` · supply-chain/publishing · **medium** · ε:no · **CONFIRMED**.
- **Claim:** Opaque publishes every wheel to the JetBrains private-namespace index and never to PyPI (`ci.yml:236-241`, `release.yml:124-133`), which is the classic dependency-confusion setup. The team recognised this and on 2026-08-12 published JetBrains security-tooling stubs on PyPI at version 999.9.9 whose description reads verbatim "This public copy of the package is a stub published on pypi.org designed to mitigate risks from Dependency Confusion" — but only for `opaque-accounting` (uploaded 15:05:40Z), `opaque-auditing` (15:05:27Z), `opaque-optimizers` (15:05:34Z) and `opaque-dpftrl` (15:05:46Z). Re-querying PyPI for all eleven names returns HTTP 404 for `opaque-base`, `opaque-engine`, `opaque-dpsgd`, `opaque-patches`, `opaque-transformers` and `opaque-alignment`, all six of which *are* really published (each returns 200 on the JetBrains simple index) and all six of which the public `README.md` package table names verbatim. The umbrella name cannot be held at all: `opaque` on PyPI is already the unrelated libopaque wrapper.
- **Failure scenario:** any third party registers `opaque-base` or `opaque-engine` on PyPI with a malicious sdist. Attacker code then executes when (a) someone installs a sub-package by bare name — the form `AGENTS.md`'s installation matrix documents (`pip install opaque-dpsgd`, `pip install opaque-engine`, …), or (b) an environment adds PyPI as an extra index alongside the JetBrains one, since pip merges candidates across indexes and prefers the highest version so a 999.9.9-style release wins, or (c) uv is configured with `index-strategy = "unsafe-best-match"`. Because `opaque-base` and `opaque-engine` are transitive dependencies of every other wheel, one captured name reaches every Opaque install in such an environment — inside a DP training pipeline handling sensitive data. The primary documented path, `pip install opaque --index-url ...`, is *not* affected: `--index-url` never consults PyPI.
- **Evidence:** PyPI JSON API for all eleven names, re-queried during verification — four 999.9.9 stubs with the quoted description and the upload timestamps above, 404 for the six named, and `opaque` 1.0.0 as a third-party project; each of the six unregistered names returns 200 on `https://packages.jetbrains.team/pypi/p/fed/python/simple/<name>/`; `.github/workflows/ci.yml:241` and `release.yml:132` publish only to that index; `pyproject.toml:83-94` `workspace.members`; `README.md:34-45` publishes the names; `AGENTS.md` installation matrix uses the bare per-package form; GitHub API `visibility: public`.
- **Fix:** ask JetBrains security-tooling (`security-tooling@jetbrains.com`, the address in the existing stubs) to publish the same 999.9.9 stub for `opaque-base`, `opaque-engine`, `opaque-dpsgd`, `opaque-patches`, `opaque-transformers` and `opaque-alignment`, and make that registration a checklist item attached to `pyproject.toml`'s `workspace.members` list so a new distribution cannot ship unregistered. For the umbrella name, which is taken, state in `README.md` and `docs/getting-started/installation.md` that `opaque` on PyPI is a different project and that the index flag is mandatory — never document a bare `pip install opaque*`.
- **Notes:** the verifier reduced this from high to medium because exploitation is not reachable from the primary documented install path and the JetBrains index is anonymously readable (verified), so users do not need `--extra-index-url`; the realistic vectors are a bare-name install or a user misconfiguration. It interacts directly with OPQ-480: the documented commands that drop the index are precisely the misconfiguration this gap needs.

**OPQ-482 — The per-package wheel build inventory in `build-distributions.yml` has no coverage guard, so a new package can ship untested and unbuilt.** `.github/workflows/build-distributions.yml:46-74` · ci-fail-open/packaging · **low** · ε:no · **CONFIRMED**.
- **Claim:** OPQ-380 named two hand-maintained inventories — the test-package matrix in `python-tests.yml` and the per-package build steps in `build-distributions.yml`. PR #870 guarded the first (`python-tests.yml:102-125` awks its own file and `comm`s it against `find packages -mindepth 2 -maxdepth 2 -type d -name tests`) and left the second untouched. `build-distributions.yml:44-74` still contains one `uv build . --wheel` for the umbrella plus nine literal `uv build packages/opaque-<name> --wheel --out-dir dist` steps (base, engine, optimizers, dpsgd, dpftrl, auditing, patches, transformers, alignment), with `opaque-accounting` built separately by maturin at `:130-163`, and nothing compares that list against `packages/*`. This is the higher-stakes inventory: a package missing from the test matrix runs no tests, while a package missing here is never built and never published. Neither downstream check closes it — `check_wheel_internal_pins.py:177-201` iterates `args.wheel_dir.glob("*.whl")`, i.e. only the wheels that exist, and `validate-distributions.yml` asserts only `len(opaque_versions) > 1` plus version equality.
- **Failure scenario:** a contributor adds `packages/opaque-<new>/` with a `tests/` tree and a pyproject. The #870 guard correctly fails the lane until `python-tests.yml` is updated, so tests get wired up; nothing forces the corresponding edit to `build-distributions.yml`. If the new package is not reachable from an `opaque[...]` extra — the common case for an optional stack — no wheel is ever built, `validate-distributions` still passes, and both the dev-wheel publish on `main` and the release publish ship a set that silently omits it. Users installing from the JetBrains index then get an `ImportError` for a package the repository documents. All ten current packages are covered, so there is no gap today.
- **Evidence:** `build-distributions.yml:44-74` (nine hardcoded steps plus the root) and `:130-163` (maturin job); `python-tests.yml:102-125` (the only inventory guard in the repository, scoped to the test matrix); `check_wheel_internal_pins.py:188-195`; `validate-distributions.yml:61-69`; `set_build_versions.sh` globs `packages/*/pyproject.toml` but only to rewrite version pins; grep over `.github` and `tests` finds no build-inventory guard; `ls packages/` returns exactly the ten distributions currently enumerated.
- **Fix:** replace the nine steps with a loop over `packages/*/pyproject.toml` (excluding `opaque-accounting`, which maturin builds), or add the same `comm`-based guard used in `python-tests.yml` as the first step of `build-python-wheels`. Stronger still: have `check_wheel_internal_pins.py` additionally assert that the set of distribution names found in `--wheel-dir` equals the set of `project.name` values across the root and `packages/*/pyproject.toml`, which makes the completeness check part of an existing behavioural gate.
- **Notes:** a partial mitigation exists and narrows the hole — `validate-distributions` installs `opaque[all]` with `--find-links dist --only-binary :all:`, and the root pyproject's extras (`pyproject.toml:33-59`) currently reach all ten distributions, so a new package wired into an `opaque` extra *would* fail resolution there. The exposure is confined to a new standalone package outside the umbrella bundle. Issue #835 (OPQ-380) is closed as completed; its acceptance criteria named only `python-tests.yml`, so this half was never in scope rather than regressed.

### 6.2 CI gates and fail-open behaviour

**OPQ-486 — A GPU runner with under 24 GB silently skips the entire Triton kernel suite and the CUDA lane still reports green.** `packages/opaque-patches/tests/kernels/conftest.py:20-48` · test-integrity/ci-fail-open · **medium** · ε:no · **CONFIRMED**.
- **Claim:** `pytest_collection_modifyitems` in the kernels conftest reads `torch.cuda.get_device_properties(0).total_memory` and returns early only when CUDA is absent or the card has at least `MIN_KERNEL_CUDA_MEM_GB = 24` GiB (`:20`). The CUDA preflight added by 039fc012 (PR #876) to close OPQ-377 probes `is_available()`, `device_count()` and one tensor add (`assert_cuda_available.sh:24-52`) and has no memory check, so it cannot distinguish an emptied lane from a real run.
- **Failure scenario:** the self-hosted runner is re-provisioned onto a smaller card (a 16 GB T4/L4/A4000 is the common case) or the `GPU-runner-001` label is repointed. All three CUDA lanes on `pr.yml` and all three on `ci.yml` then run `-m 'cuda and not slow'` / `-m cuda`, collect the kernel tests, skip 100 % of them at collection, and pass. Proven functionally rather than assumed: loading that conftest, stubbing `torch.cuda.is_available()` → True and `get_device_properties()` → 16 GiB, and feeding it one item per kernels test file plus one dpsgd item marks 19/19 kernel files and 0 items outside the directory, with reason `Kernel stress tests require >= 24GB CUDA memory (found 16.00GB).` The lost selection is 225 of the 397 tests in that directory under `-m 'cuda and not slow'` — the only validation of the Triton kernels the DP-SGD `vmap(grad)` pipeline runs on GPU. `publish-dev-wheels` (`ci.yml:199-213`) needs exactly those jobs, so `main` keeps publishing dev wheels on unvalidated kernels. The lane passes `-rs` so the skips appear in the log, but nothing fails on them.
- **Evidence:** `packages/opaque-patches/tests/kernels/conftest.py:20` (`MIN_KERNEL_CUDA_MEM_GB = 24`) and `:36-48` (unconditional directory-wide marking); the functional proof above; `pytest --collect-only -m 'cuda and not slow' packages/opaque-patches/tests/kernels` → 225/397 collected; `.github/scripts/run_python_test_package.sh:38-48`; `.github/scripts/assert_cuda_available.sh:24-52`; `.github/workflows/python-tests.yml:76-81` places `packages/opaque-patches` in the `runtime-and-patches` suite the CUDA lanes run; `.github/workflows/ci.yml:199-213`.
- **Fix:** scope the gate to the tests it was written for — mark the stress/perf cases explicitly (e.g. `@pytest.mark.kernel_stress`) and skip only those, leaving the numerical-parity tests to run at whatever size the card allows, since most already use tiny shapes and only the MELLUM config cases need 24 GB. Independently, make the lane fail rather than pass on a fully-skipped selection: have `run_python_test_package.sh` parse the summary (or use a strict-nonempty plugin) and fail when `selected > 0 and passed == 0`, and extend `assert_cuda_available.sh` with a minimum-memory assertion keyed to `MIN_KERNEL_CUDA_MEM_GB` so a too-small card fails the lane instead of emptying it.
- **Notes:** latent — triggering requires the self-hosted runner to be re-provisioned, and the live runner's card could not be inspected, so no library behaviour is wrong today. Not a duplicate of open #880 (two kernel files missing `pytest.mark.cuda` — different trigger, different files), though #880's acceptance criterion about asserting a minimum collected-test count would fix half of this; #774 is the natural umbrella.
