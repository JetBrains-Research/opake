## 2. Regressed, not fixed, and partial — worst first

### 2.1 REGRESSED — Slate #397, sliding-window attention semantics

**This is the most important item in the report.** A fix that was verified in July, verified again in August, and re-verified as still-correct in this run was undone in September by performance work, and the result silently changes what the model computes.

The July dense-mask fix is intact. The August high-severity residual (SDPA with `attention_mask=None`, Bazalt `#811` / OPQ-337) was fixed correctly by `171da1c7` (#877) and I reproduced that: with `attn_implementation='sdpa'`, `attention_mask=None`, `sliding_window=4`, `seq=12`, patched logits are bit-identical to clean out-of-process upstream references on transformers 5.15.1 / torch 2.13 for mistral (7.7641603413794655 both), gemma3 (22.49240287952125 both), cohere2 (1.5250016759855498 both) and phi3 (-6.6575579488126095 both), with a window-free control producing visibly different values. A boundary sweep at `seq=3,4,5,6,9` with `sliding_window=4` is bit-exact, so the skip predicate at `runtime/masking.py:370,381` has no off-by-one.

Then the compact-mask performance series reopened it. `4e61b09d` (#925) and `d80d3f99` (#954, Sep 6) gave mistral, ministral and gemma2 `vmap_create_compact_sdpa_sliding_window_causal_mask`, which deliberately returns `None` — no mask at all — whenever `_can_use_compact_sdpa_sliding_window` holds (`packages/opaque-patches/src/opaque/api/patches/transformers/runtime/masking.py:78-107`), on the assumption that the family's patched SDPA forward applies the look-back limit itself. That assumption is encoded twice, in two independently written predicates, and they diverge in both directions.

**Failure (a) — gemma2 with softcapping disabled attends to the full context** (findings 36 and 57, both high). `vmap_sdpa_attention_forward_gemma2` (`packages/opaque-patches/src/opaque/api/patches/transformers/components/attention.py:670-738`) consumes `sliding_window` only inside its `if softcap is not None:` branch at `:683`. When `Gemma2Attention` passes `softcap=self.attn_logit_softcapping=None`, it falls through at `:729-738` to `vmap_sdpa_attention_forward(...)`, which has no `sliding_window` parameter at all (`:174-241` does causal SDPA only) — and because `sliding_window` is a *named* parameter of the enclosing function at `:678`, it is not in `**kwargs` either. It is dropped entirely. The mask builder elided the window; the forward never applied it.

Reproduced end to end, tiny Gemma2 (hidden 64, 2 layers, default alternating `layer_types=['sliding_attention','full_attention']`, `sliding_window=4`, `seq=12`, sdpa, `attention_mask=None`, `attn_logit_softcapping=None`), logits summed in separate processes on identical seeded weights: upstream `10.66509758651955`, opaque-patched `19.25782148790313`, upstream with the window disabled `19.25782148790313`. The patched model reproduces the *no-window* reference to the last digit. With softcapping at its 50.0 default: `10.664953630010132` vs `10.664955383865163` — fp32 noise. At unit level, `vmap_sdpa_attention_forward_gemma2(..., softcap=None, sliding_window=3)` differs from a dense windowed reference by 1.16 and from a dense no-window reference by 1.19e-07. The trigger profile is identical to OPQ-337's: supply an all-ones `attention_mask` and it matches exactly; use `attn_implementation='eager'` and it matches exactly.

At the delta base (`git show 4b13d82:.../components/attention.py:160-196`) the gemma2 softcap-`None` branch delegated to stock `sdpa_attention_forward` and gemma2 had no masking patcher, so the dense mask always carried the window. **The hole is new in this delta.** `models/gemma2.py:35` is the line that opened it.

**Failure (b) — mistral in train mode under no_grad** (finding 36). The builder admits the elision when `not torch.is_grad_enabled() or config.attention_dropout == 0.0` (`masking.py:103-105`), while `vmap_sdpa_attention_forward_sliding_window` requires the *runtime* `dropout == 0.0` (`attention.py:297`). In `train()` + `no_grad()` with `attention_dropout=0.1` and `dropout=False`, the builder elides and the forward declines. Reproduced: upstream `7.156000263028545`, patched `4.206265495965454`, upstream with `sliding_window=64` `4.206265495965454`.

Nothing asserts that the forward applied what the builder skipped. Both paths fail open. The fix is to make elision and application one predicate rather than two: route the gemma2 `softcap is None` fall-through through `vmap_sdpa_attention_forward_sliding_window(..., sliding_window=sliding_window)`, and have that function build the band mask itself rather than falling back to the window-blind `vmap_sdpa_attention_forward`. The existing sliding-window parity variant always supplies a mask, so this branch is untested — a parity case with `attn_logit_softcapping=None`, `sliding_window < seq_len`, sdpa and no mask is required.

Note the cross-milestone shape: Slate `#397` reads **regressed**, Bazalt `#811` (OPQ-337) reads **fixed-with-caveats**, and they are the same defect. The August fix is correct; the September perf work reopened the class in sibling paths.

### 3.3 `_compile_with_fullgraph_fallback` — `f55c2a89` then `fae93a55`. Closes `#821`.

**Removal: internally coherent. Behaviorally, it took a feature with it.**

Two steps. `f55c2a89` first narrowed the handler to `torch._dynamo.exc.TorchDynamoException` exactly as the fix sketch asked, so `torch.OutOfMemoryError` propagated to the trainer's OOM path. `fae93a55` then deleted `_compile_with_fullgraph_fallback` outright and replaced it with `_compile_strict_chunk` (`:209-219`), which compiles only the tensor-only chunk kernel with `fullgraph=True`, `dynamic=True`, no fallback and no exception handling — so the reported double-execution and the misleading warning are both structurally unreachable.

No dangling references; the docs were updated to drop the "falls back with a warning" language (`docs/reference/transformers.md:218`, `docs/user-guide/huggingface/training-arguments.md:216`); and `training_step`'s failure path was rebuilt around `_synchronize_grad_failure` (`:1322-1348`), which re-raises the original exception on a single process and MAX-all-reduces OOM vs non-OOM flags under DDP.

**User-facing capability lost with no replacement — this is the one to escalate.** What used to degrade to `fullgraph=False` now aborts the run, and `torch_compile=True` is consequently **unusable with Hugging Face models** (findings 33, 34, 91). Three independent causes now sit on that one switch:

- `_dp_trainer.py:209-219` — the fullgraph fallback was deleted, not narrowed, so the first graph break is fatal (finding 33).
- `_dp_trainer.py:218` — `dynamic=True`, added by the Poisson graph-reuse change `afa0247f` (#989), makes `clipping_mode="auto"` + `torch_compile` crash even with no graph break (finding 34).
- Finding 91 (high) — the now-default fused loss-only CE forward is not Dynamo-traceable under `fullgraph=True`, so `torch_compile=True` aborts DP training on the first step for **every supported dense HF causal-LM family** (`components/cross_entropy.py:257-259`, `kernels/_linear_ce_chunked.py:88-101,120`, `_dp_trainer.py:209-218,2437-2442`, `_factory.py:374-381`).

The removal was the right call on its own terms. Nobody then checked whether `torch_compile=True` still worked. It does not.

### 6.2 New Poisson PLD amplification math (#850) — the deepest single piece of work in this audit

Reviewed as new mathematics from first principles, not against the repository's own oracle:

- The generalized amplification statement was **derived independently**: for a base pair (P,Q), Poisson-q gives `H_gamma((1-q)Q+qP || Q) = q * H_{(gamma-1+q)/q}(P||Q)` for gamma ≥ 1-q and `1-gamma` below that, and `H_gamma(Q || (1-q)Q+qP) = (1-gamma(1-q)) * H_{gamma q/(1-gamma(1-q))}(Q||P)`. Each direction is a pure monotone reparametrisation of the *same* direction's hockey-stick curve, so one-sided hockey-stick domination of the base is exactly sufficient — no stochastic dominance needed.
- Confirmed against the primary source: arXiv:2602.17284 (Feldman & Shenfeld, "Efficient privacy loss accounting for subsampling and random allocation"), which states after Theorem 3.3 that domination is preserved under the subsampling transformation. Its Claim B.2 says stochastic domination is **not** preserved under subsampling/dual — so every call path was checked for feeding a `poisson_pld` output into the random-allocation transform, the only transform whose module doc (`pld/realization.rs:1-13`) requires first-order stochastic dominance. None does: `random_allocation_gaussian_pld` builds its own analytic `NormalLoss` and never takes an external PLD.
- Both transforms verified algebraically against the implementation. REMOVE (`poisson.rs:311-339`): for each base atom (L,m) the code emits loss `log(1-q+q e^L)` and mass `m*((1-q)e^-L + q)`; substituting `A = 1-q+q e^L` gives `m'(1-e^{eps-L'}) = q*m*(1 - gamma_b e^-L)` exactly, the +inf atom maps to `q*M_inf`, and the dual-residual atom at `log(1-q)` with mass `(1-q)(1-E[e^-L])` makes the total mass sum to 1 and makes `delta = 1-gamma` in the trivial region. ADD (`poisson.rs:341-355`): loss → `-log(1-q+q e^-l)`, masses unchanged, base +inf atom mapped to the finite maximum `-log(1-q)`, output ADD pmf carrying `infinity_mass == 0` — correct, since `P_q = (1-q)Q + qP` is never null where Q is positive.
- Conservatism measured, not assumed, across roughly 1,000 configurations: 126 (sigma, q, n) points against the old binary and Google `dp_accounting`'s connect-the-dots PLD (old path matched Google to ~1e-9; new path conservative in **every** case, worst over-estimate 0.16% relative at sigma=8/q=0.9/n=500, ~5e-5 at typical DP-SGD settings); 384 (sigma, q, eps) points against an independent 60-digit mpmath closed form for the subsampled-Gaussian hockey stick in both adjacency directions (zero underestimates); 162 points for the non-Gaussian-source general path against the closed form at sigma/sqrt(k) (zero underestimates); 400 points of `poisson_pld(eps_delta_pld(e0,d0), q)` against an exact four-atom transform of the canonical dominating pair (zero underestimates); 48 old-vs-new configurations showing the generalized transform uniformly 0.00–0.03% **looser**, never tighter.
- Boundary handling sound: the native primitive rejects `rate` outside (0,1) including NaN, and `Poisson.__post_init__`/`pld()` intercept `sample_rate == 1.0` in Python and return the base PLD. The `gaussian_source` fast path (`mechanisms/gaussian.rs:32-40`, `pld/mod.rs:171-178`) is safe because `compose`/`self_compose` clear the tag (`pld/mod.rs:500`, `:558`), so only pristine `gaussian_pld` outputs take the shortcut. `realization_source`'s repairs are all conservative: missing mass goes to +inf, the `E[exp(-L)]<=1` repair moves finite mass to +inf, and the >1 excess trim is bounded by `REALIZATION_MASS_TOLERANCE=1e-8`.

Two consequences to record. **Reported epsilon shifts slightly upward for every Poisson config versus v0.15.x** — which matters for any previously published number. And the factory now accepts any `DpProcess` rather than only Gaussian/AdaClip/NonPrivate, which removed the inner-type guard: findings 7, 86 and 96 (medium) show `dpsgd_acc.poisson()` silently amplifying already-amplified and whole-horizon processes and reporting a *smaller* epsilon (`dpsgd/amplification/_poisson.py:21,39-47,158-173`), with the sibling guard for `ParallelPoisson` living only in the factory so direct construction and deserialization bypass it (finding 88). Finding 87 adds that the generic transform costs ~4 orders of magnitude of tightness against the external oracle and the cross-validation tolerances were relaxed 60×–220× to absorb it (`test_cross_validation.py:47-57,265-267,343-346,389`).

### 6.5 Privacy invariants, derived rather than assumed

- **Clipping sensitivity bound (fixed and AUTO-S):** `clipped_grad`/`auto_clipped_grad` run with `return_aux` over fp16/bf16/fp32 × gradient scales 1e-4..1e3 × C in {1e-4, 1, 1e4} × gamma in {1e-8, 1e-2} × microbatch {off, 2}; max observed `‖clip(g)‖/C` = 0.99999990, never above 1. The `_guard_scale`/`_scale_tensor` rework (`026200fd`) holds the bound when the multiply happens at wider precision, and AUTO-S rejects gamma=0. A separate float64-exact fuzz of the halved bf16 margin (~0.8% → ~0.4%) across four storage dtypes × five compute dtypes, scalar and PerGroup, 1-element to 200k-element leaves, magnitudes 1e-6..1e4: worst 0.99999988 (fp32), 0.9962 (bf16), never above 1, never collapsing the scale to zero.
- **Per-group noise allocation:** the Mahalanobis budget was derived — `sigma_g = nm*sqrt(B_g * sum_h B_h)` gives `sum_g (B_g/sigma_g)^2 = 1/nm^2` exactly, so the per-group Gaussian has the same PLD as `gaussian(nm)` with no penalty in the number of groups — and the clip-group and noise-group path assignments were shown to be the identical mapping.
- **Paired first/second-moment budget:** `sum_g[(Delta1/sigma1)^2 + (Delta2/sigma2)^2] = (c1/nm)^2`, matching `mf_gaussian_pld(nm, c1)`/`gaussian(nm)` for the DP-SGD identity case; the shipped squared-stream bound `C^2/normalize_by` is a valid bound on `‖g ⊙ g‖_2`, including per-group.
- **k-out-of-t sampler vs its accountant:** `KOutOfTSampler.block_sizes = (floor,)*(k-m_c) + (floor+1,)*m_c` matches the Rust decomposition at `amplification/random_allocation.rs:186-221`; unequal blocks are priced at their own higher per-step probability, not an averaged `t/k`. Blocks are independently keyed via `fold_in(stream_key, block)`, `_total_batches` implements the exact conditional k-subset draw, and it replays deterministically on resume. Exactly-k participation and exactly-one-per-block verified empirically for (k,t) in {(3,10),(4,19),(2,8),(5,5),(1,7)}.
- **BandMF min-separation sensitivity:** `max_participation_for_linear_fn` hand-verified as the correct at-most-k/min-sep dynamic program; `minsep_sensitivity_squared` shown to reconstruct `‖sum_{j in pi} C[:,j]‖^2` for the equally-spaced pattern including the k-truncation subtraction (and the RHS is evaluated before the in-place slice write, so overlapping slices are not a bug); the reverse-cummax majorant verified sound for signed/non-monotone columns.
- **Rounding directions on the Rust conservative-bound math:** `alloc_remove` rounds Up throughout; `alloc_add` deliberately rounds the inner convolution Down because an upper bound on `-ln(S)` needs a lower bound on S, then rounds the final projection Up (`random_allocation.rs:105-130`). `toeplitz_majorant_sensitivity_squared` uses a reverse-suffix-max of |c| (`bisr.rs:249-257`), both a pointwise majorant and non-increasing as the Toeplitz theorem requires. The BISR |C| substitution (`gram_matrix.rs:235-242`, `bisr.rs:160-171,386-390`) is the row-wise triangle inequality and yields a Gram of the form M'ᵀM', so it stays PSD.
- **`numerics/fft.rs` strategy rewrite**, which now *prefers* the aliasing circular transform whenever a tail budget exists and the bounded transform is ≤¼ of the alias-free one: checked for soundness rather than assumed. Circular aliasing only folds mass from outside `[lower, upper]` back into the window, never removes in-window mass, and `delta_at` is monotone non-decreasing in every bucket mass, so `delta_circular >= delta_linear-truncated` always; the same out-of-window mass is separately and conservatively charged to `infinity_mass`/`negative_infinity_mass` in `Pmf::self_compose` (`pld/pmf/dense.rs:352-366`). A/B over `self_compose` n in {2,10,50,100,500,1000,5000} at sigma in {1,3} shows at most 1.4e-9 absolute epsilon difference in either direction, with both builds the same ~1.7e-8 relative below the analytic Gaussian — a pre-existing discretisation artifact reproduced identically by the pre-delta binary, not a regression.

Two high findings came out of this area anyway: finding 12/140 (`IdentityStrategy.sensitivity` ignores the participation schema, so bare `mf_gaussian` under-reports epsilon by sqrt(k) — 145× at the default horizon — `dpftrl/noise/_identity.py:45-46`, the one sibling the `#998` participation-schema fix did not convert) and finding 141 (paired second-moment MF release never tied to an accountant; a documented mismatched-strategy pair is 1.31× under-noised, `_second_moment.py:140-150`). Finding 94 (high) adds that adaptive clipping releases a {0,1} clipped-count query while AdaClip accounting prices it at {-1/2,+1/2} sensitivity, under-pricing the quantile release 2× in mu and 4× in variance.
